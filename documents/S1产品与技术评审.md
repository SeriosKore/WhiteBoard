## 一、总评

**范围划分基本合理，架构方向正确，但有 2 类问题必须在开工前解决：**

| 类别 | 问题 | 严重度 |
|---|---|---|
| **产品** | S1 目标写的是"能上一节课"，但**缺少几个课堂刚需功能**（全屏、清空页、键盘翻页、复制页、颜色/笔宽），按现状交付，老师上完一节课会卡手 | 🔴 高 |
| **产品** | **保存后找不到文件**：默认落 `data\documents\`，老师不知道在哪，也没有"最近文件"入口 | 🔴 高 |
| **技术** | **湿/干笔迹外观不一致**：湿笔迹由 `InkCanvas` 渲染、干笔迹由手绘风格渲染器渲染，抬笔瞬间笔迹会"变样子"，极易被当成 bug | 🔴 高 |
| **技术** | **WPF 三路输入（笔/触摸/鼠标）会重复触发**，若不在输入层设计阶段定死抑制策略，会出现"画两遍" | 🔴 高 |
| **技术** | 文本工具就地编辑与中文 IME 是深坑，形态未定 | 🟠 中 |
| **技术** | 撤销栈的跨页语义未定 | 🟠 中 |

**结论**：建议将 6 类课堂刚需/打包能力纳入 S1（**约 +9.5 人日**），并从风险缓冲中消化，工期维持 10 周（WBS 由 73 人日增至约 82 人日 / 20 人周，仍有约 17.5% 缓冲）。

## 二、产品评审

### 2.1 做对的地方（建议保留并强化）

| 项 | 评价 |
|---|---|
| **M0 止损闸门** | 极高价值。7~11 人日换"框架选错"的早期发现，性价比最高的投入 |
| **湿/干笔迹分离** | 正确解法，直击上次失败的根因 |
| **数据自包含 + 无回退链** | 明确报错优于静默把数据写散，符合 C3 |
| **出口准则含"真实课堂试用 + 非开发人员独立部署"** | 好，这两条最能戳破"开发自嗨" |
| **A13 可搬运性** | 直接验证"绿色便携"这个核心卖点 |

### 2.2 产品缺口（建议补入 S1）

#### 🔴 G1 · 缺全屏/放映模式

一体机课堂上，老师是在**学生面前**操作。带标题栏和任务栏的窗口：
- 占掉可见区域，板书区域变小；
- 学生看到"Windows 窗口"，没有"白板"的沉浸感；
- 老师无法用最大的画面空间书写。

**建议**：S1 加入全屏切换（`F11` + 工具栏按钮 + `Esc` 退出）。成本约 **0.5 人日**。

#### 🔴 G2 · 缺课堂高频操作

| 功能 | 为什么是刚需 | 成本 |
|---|---|---|
| **清空当前页** | 老师每节课要用很多次（讲完一题擦干净） | 0.3 d |
| **键盘翻页**（`PageUp/PageDown`、`←/→`） | 老师一手拿教鞭/一手在屏上写，腾不出手点缩略图 | 0.3 d |
| **颜色 + 笔宽调整** | "画"这件事离不开颜色与粗细；计划书完全没提调色板与笔宽 | 2 d |
| **撤销/重做的显眼入口** | 有命令栈但没提 UI 入口；老师不会去记 `Ctrl+Z` | 0.3 d |
| **复制当前页** | 同一道题讲两遍、留一页做草稿，教学高频 | 0.5 d |

**合计约 3.4 人日。**

#### 🔴 G3 · 保存后"文件在哪"不可见

计划书 5.4 的设计是"不弹对话框，直接落 `data\documents\<时间戳>.wb`，状态栏提示"。这个思路（不打断课堂）是对的，但**缺了闭环**：

- 老师下课后想把这个文件拷走或发出去，**找不到**；
- 状态栏一闪而过，老师根本没注意。

**建议补三项（约 1.5 人日）**：
1. **最近文件**入口（首屏或"文件"菜单），点击直接打开，右键"打开所在文件夹"；
2. 首次保存后给一次**非阻塞提示**："已保存到 …（点击打开文件夹）"，带"不再提示"；
3. 保存路径在标题栏或状态栏**常驻显示**文件名（当前文档名）。

#### 🟠 G4 · 导出体验过于单薄

计划书只写"逐页导出 PNG"。老师导出图片的真实用途是**放进 PPT** 或**发班级群**。20 页要点 20 次不可接受。

**建议补（约 1 人日）**：
- **批量导出全部页面**（一次导出到同一文件夹，按页码命名）；
- 导出后提供"打开所在文件夹"；
- 可选：**复制当前页到剪贴板**（粘贴进 PPT 最省事）。

#### 🟠 G5 · 缺快捷键说明

老师不会用就等于没做。建议在"关于"旁边加一个**快捷键一览**（一个静态对话框即可，0.2 人日）。

#### 🟡 G6 · 页面背景（方格纸 / 四线三格）

数学课要方格、语文课要田字格/四线三格。这是**教学内容的一部分**，不是装饰。S1 完全没提。

背景是文档属性，影响渲染、导出与序列化，**格式现在就该定**。建议 S1 做"纯色 + 方格纸"，四线三格放 S2（见待决策 Q6）。

## 三、技术评审

### 3.1 架构判断（认可）

| 项 | 评价 |
|---|---|
| 湿/干笔迹分离 | ✅ 正确，且是唯一正确解法 |
| 模型层不依赖 UI 框架 | ✅ 可单测、可换壳 |
| `PathService` 统一可写路径、无回退链 | ✅ 符合 C3 |
| 几何用**局部坐标缓存 + 变换矩阵**（而非平移时重建几何） | ✅ 正确，平移缩放只换矩阵，几何可 `Freeze()` 复用 |
| 手绘抖动用**对象 Id 派生 seed**（确定性） | ✅ 避免重绘闪烁；⚠️ 注意克隆/复制对象必须重新生成 Id，否则抖动图案重复 |
| 撤销用命令模式 + 事务 | ✅ 正确 |

### 3.2 技术风险与模糊点

#### ✅ T1 · 湿/干笔迹外观不一致 —— **已解决（改平滑风）**

**原判断**：湿笔迹由 `InkCanvas` 用自己的笔尖模型渲染（`DrawingAttributes` + `FitToCurve` + 压感），干笔迹由我们的 `HandDrawnRenderer`（抖动 + 二次贝塞尔）渲染。**两者外观必然不同** → 抬笔瞬间笔迹"变样子"。

**实测确认**：PoC-A 人工核验 —— 差异**非常明显**。

**决策：笔迹与图形一律改平滑风，放弃手绘抖动风。**

**并且验证到位了**：同一组 160 点 + 同一份 `DrawingAttributes`，三条干渲染路径与 `InkCanvas` 湿渲染逐像素比对：

| 干笔迹渲染方式 | 差异像素 | 占比 |
|---|---:|---:|
| `stroke.Draw(dc)` | **0** | **0.000%** |
| `dc.DrawGeometry(brush, null, stroke.GetGeometry())` | **0** | **0.000%** |
| `dc.DrawGeometry(null, pen, stroke.GetGeometry())`（描边） | 14 119 | 1.681% |

→ 采用**几何填充**方式即可做到抬笔**零外观突变**，且几何可冻结缓存（构建耗时 ≈0 ms）。**原方案的"淡入过渡掩盖"不再需要。**

> 副作用全为正：省掉自研抖动/平滑算法（S1 的 T2.4 由 4 d 降到 2.5 d）、风险 R6 关闭、外观还更干净。
> ⚠️ 这是对原始需求"所有图形采用手绘风格渲染"的**变更**，已由需求方确认（见总路线 ADR-09）。

#### 🔴 T2 · WPF 三路输入的重复触发

触屏上 WPF 先抛 `TouchDown` 再**合成** `MouseDown`；电磁笔先 `StylusDown` 再合成 `MouseDown`。若三路都接，会**画两遍 / 交互两次**。

- 必须在**输入层设计阶段**就定死"优先级 + 抑制策略"（不是后期能补的）。
- **建议**：优先级 `Stylus > Touch > Mouse`，一旦某路接管本次交互，其余路的合成事件一律 `Handled = true` 吃掉。
- 这条我按建议直接写入设计，不再单独征询（如你有异议请提）。

#### 🟠 T3 · 双指手势与单指绘制冲突

用 WPF 的 `Manipulation*` 事件，还是自己算触点？混用会冲突。更关键的是**边界规则**：

> 笔画进行到一半，第二根手指落下了，怎么办？

| 选项 | 行为 | 优点 | 缺点 |
|---|---|---|---|
| **① 第二指落下即终止笔画 + 进入手势** | 立刻结束当前笔画，转为缩放/平移 | 符合"想缩放就上手"的直觉 | 书写时手掌/手指误触会**打断笔画** |
| **② 忽略第二指直到笔画结束** | 笔画继续，第二指被忽略 | 书写不被打断，防误触 | "画到一半想缩放"必须先抬手 |
| **③ 需长按/停顿才进入手势** | 更保守 | 最防误触 | 有学习成本 |

（见待决策 Q4）

#### 🟠 T4 · 掌拒策略

WPF 无系统级掌拒，需自实现。选项：(a) 触点面积阈值；(b) 屏幕边缘区域忽略；(c) **笔靠近时禁用触摸**（`StylusInAirMove` / `StylusOutOfRange`，最有效，但要求设备支持悬浮检测）；(d) 不做。

**建议 (c) + (a) 组合**，降级到 (a)。无目标机型时无法充分验证，需在验收时补测。

#### 🟠 T5 · 文本工具的形态与 IME

在自绘画布上做"就地编辑"是**中文 IME 的深坑**（候选窗定位、composition 事件、光标绘制都要手写）。

**建议路线**：编辑时在画布对应位置**叠加一个真正的 `TextBox`**（透明背景、同步字号与位置），编辑完成转为 `TextObject`。IME 天然可用，成本最低。

**连带决策**：S1 的文本**是否支持旋转**？建议**否**（旋转后的 TextBox 定位与文字方向会显著增加复杂度），旋转文本留到 S2。

（见待决策 Q3）

#### 🟠 T6 · 撤销与跨页语义

三个子问题：

| 子问题 | 选项 | 建议 |
|---|---|---|
| 撤销栈是全局还是每页一个？ | ① 全局单栈 ② 每页独立栈 | **全局单栈** |
| 在 B 页撤销 A 页的操作时，视图是否自动切回 A 页？ | ① 自动切回 ② 不切（用户看不到效果） | **自动切回** |
| 切换页面本身是否进撤销栈？ | ① 进 ② 不进 | **不进**（否则撤销会莫名其妙切页） |

（见待决策 Q5）

#### 🟡 T7 · 自动保存的线程模型

60 s 一次全量序列化，大文档可能 **100~500 ms** 卡顿，在 UI 线程上会造成周期性顿挫。

| 选项 | 做法 | 代价 |
|---|---|---|
| **(a) 主线程 + 增量节流** | 只序列化**脏页**，且等"无笔画进行中"时触发 | 简单、无锁；仍有短顿挫 |
| **(b) 后台线程 + 对象图快照** | 模型不可变或深拷贝后后台序列化 | 无顿挫；需投入不可变设计或深拷贝成本 |
| **(c) 后台线程 + 加锁** | 简单加锁 | 简单但仍有停顿与死锁风险 |

**建议 (a)**：S1 先做增量 + 空闲触发，把 (b) 留给 S2 性能专项。**需你确认可接受的自动保存卡顿上限**（建议 ≤50 ms）。

#### 🟡 T8 · 序列化精度与文件大小

`double` 全精度序列化会产生 `123.45678901234567` 这样的长数字。选项：
- **全精度** → A6"往返一致"可**严格比对**，但文件偏大（靠 ZIP 压缩缓解）；
- **取整 3~4 位** → 文件小，但 A6 只能**容差比对**。

**建议全精度**（往返精确 + 验收可严格判定）。如你更在意文件大小再改。

#### 🟡 T9 · 笔迹路径简化是否 S1 做

500 笔 × 200 点 ≈ **10 万点**，不简化将同时影响渲染与文件大小。Douglas-Peucker 是成熟算法（约 50 行）+ 输入时最小距离过滤。

**建议 S1 就做**（约 1 人日，收益大）。

#### 🟡 T10 · 撤销栈内存上限

100 步 × 每步可能持有大对象快照（如整页擦除）。**建议加内存上限**（步数与总字节数取小），溢出时**丢弃最早的**（而不是停止记录，否则用户会以为撤销坏了）。

#### 🟡 T11 · `--self-test` 骨架应提前到 S1

S3 的插件自检要复用这个能力。**建议 S1 就搭骨架**（约 0.5 人日），否则 S3 要返工改造。

#### 🟡 T12 · 性能验收口径不可测

A3 写的是"500 笔无卡顿，内存 <500 MB"——"无卡顿"**无法判定**。

**建议改为**：绘制/拖动时 **≥50 fps（目标 60 fps）**，对象数 500 / 页数 20；并注明测试机器的配置档位。（见待决策 Q7）

#### 🟡 T13 · 缩略图的刷新策略与性能

20 页缩略图若每次编辑都刷新当前页，会持续占用 CPU。

**建议**：脏页标记 + **500 ms 防抖** + 只刷新脏页；缩略图分辨率低（宽约 160 px）。

#### 🟡 T14 · 导出 PNG 的尺寸上限

`RenderTargetBitmap` 在"内容边界"很大时（4K 内容 + 高 `pixelsPerUnit`）可能内存爆或抛异常。

**建议**：设上限（最长边 ≤ 8000 px），超过则等比缩小并在 UI 提示。

#### 🟡 T15 · 跨显示器 DPI 变化

多显示器之间 DPI 不同时，WPF 需要 PerMonitorV2 感知 + 重建渲染目标。

**建议**：S1 只保证**单显示器正确**，跨屏 DPI 变化列为已知限制（S2/S4 处理）。（见待决策 Q8，可后置）

#### 🟡 T16 · `.wb` 格式必须现在就为 S2 留好扩展位

S2 要加图片对象、新形状、页面背景。S1 的格式必须：
- 多态类型注册表机制（`[JsonPolymorphic]` + 类型判别字段）；
- 加载时遇到**未知类型**要"跳过 + 提示"，而不是崩溃；
- `images/` 目录机制现在就建好（即使 S1 用不上）。

否则 S2 会推翻 S1 的存储层。

#### 🟡 T17 · CI 平台未定

计划写"CI"但未指定。若无在线 CI 服务，**建议以本地一键脚本为主**（构建 + 单测 + 打包 + 白名单审计 + 干净环境验证），CI 可选。

### 4.0 ✅ 已决策：页面级操作的撤销归属

"每页独立撤销栈"（Q5）在 S1 留下一个**无处安放的类别**：

> **新建页 / 复制页 / 删除页 / 追加导入 —— 这些操作不属于任何单一页面的内容，没有归属的栈。**

若硬塞进"当前页"的栈，用户会遭遇「在 A 页按 `Ctrl+Z`，结果删掉了一整页」的惊吓。

**决策：方案一 —— 页面级操作不进撤销栈，改用「确认 + 补偿入口」**

| 操作 | 处理 |
|---|---|
| 新建页 / 复制页 | 无需撤销（无害，不需要就删掉） |
| **删除指定页** | **入口在页面目录：每个缩略图提供删除按钮**（用户明确要求）→ 确认对话框 → 页面进入"最近删除"，可一键恢复 |
| 追加导入 | 完成后显示**非阻塞提示条**「已追加 n 页 · 撤销」，点击即整体移除本次导入的页 |

**配套边界规则**：文档至少保留 1 页（删最后一页自动补空白页）；删除当前页后自动跳到相邻页（优先前一页）；"最近删除"仅在当前会话内保留。

> 备选方案（另设"文档级栈"）已否决：`Ctrl+Z` 该撤销哪一层会让人困惑，且与 Q5 的简洁语义相冲。

### 4.0-Q4 · ⚠️ Q4 的实现细化（编码时发现原决策会锁死手势）

**原始决策**：笔画进行中"忽略第二指，直到笔画结束"。

**实现时发现的问题**：第一根手指按下就**立即**开始笔画，因此"没有笔画进行"这个状态在触摸场景下**几乎不存在** —— 按原决策实现后，**两指缩放/平移将永远无法触发**。单元测试 `Test_Router_TwoFingersQuicklyStartsGestureAndCancelsStroke` 复现了这一点。

**细化后的规则（按"手势判定窗口"分界）**：

| 第二指到来的时机 | 行为 |
|---|---|
| 笔画开始后 **≤150 ms 且已采点 ≤6** | **取消这点头笔画，进入手势**（判定为"用户想缩放"） |
| 超出该窗口 | **忽略第二指，笔画继续**（判定为误触，保护书写） |

**为什么这样取舍**：
- 若改成"第一指按下后延时等待第二指"，单指书写就会有可感知的起笔延迟 —— **对白板是致命的**（M0 的延迟目标 ≤1 帧）；
- 若永不取消笔画，两指手势无法触发；
- 150 ms / 6 点这个窗口在两者之间取得平衡，且**笔（Stylus）不参与手势、完全不受影响**，始终零延迟。

**已落地**：`PointerRouter.GestureWindowMs = 150`、`GestureMaxPoints = 6`；`RouteResult.CancelledStroke` 通知调用方丢弃当前笔画；3 个单元测试覆盖窗口内外与手势数学。
### 4.1 ✅ 已决策：跨页操作采用方案 A（S1 暂不实现）

Q5（每页独立撤销栈）对 S1 是干净利落的，但与 **S2 的"跨页复制/移动"**冲突——后者原设计要求"记录命令以支持撤销"。

- 一次跨页移动 = 源页"删除对象" + 目标页"添加对象"；
- 若两条命令分别进两页的栈，用户按一次 `Ctrl+Z` 只撤销了一半 → 出现**对象重复出现**或**两边都消失**的不一致状态。

**决策：方案 A** —— 两条命令**配对互引**，撤销任一条时同时回滚两侧，并自动切回源页。已写入 S2 的 T6.5 与总路线 R9。

**并且 S1 不实现跨页操作**（开发方评估结论，详见 `计划书_S1_基础版.md` §八 8.1）：S1 已纳入"复制当前页"覆盖多数场景，跨页事务推迟以保住 19.5% 的缓冲。

### 4.2 ✅ 已决策：红蓝调亮，`color.txt` 改为程序标准格式

原内容（CSS 自定义属性语法）：

```css
--board-bg:    #2F4F3A;  /* 黑板绿，纯色背景 */
--chalk-white: #F5F5F0;  /* 白笔 */
--chalk-yellow:#EED858;  /* 黄笔 */
--chalk-red:   #E04D40;  /* 红笔 */
--chalk-blue:  #5485C9;  /* 蓝笔 */
```

**对比度（按 WCAG 相对亮度实测）与处理结果**：

| 颜色 | 对黑板绿 `#2F4F3A` | 原判定 | **处理** | 调后 |
|---|---:|---|---|---:|
| 白 `#F5F5F0` | 8.4 : 1 | ✅ 优秀 | 不变 | 8.4 : 1 |
| 黄 `#EED858` | 6.4 : 1 | ✅ 良好 | 不变 | 6.4 : 1 |
| 红 `#E04D40` | 2.3 : 1 | ⚠️ 偏低 | **调亮为 `#F47A6E`** | **3.4 : 1** |
| 蓝 `#5485C9` | 2.4 : 1 | ⚠️ 偏低 | **调亮为 `#6E9FE0`** | **3.4 : 1** |

四色现已全部达到 3:1 图形下限。

**文件格式已改为程序标准（JSON）**：

- 用户明确：该文件**后期用于保存用户的预设**，目前只是给开发方读取的参考，**格式按程序标准走**；
- 因此不再沿用 CSS 变量语法，改为 JSON（`version` / `defaultPreset` / `presets[]` / 每套预设含 `backgroundType`、`background`、`colors[]`），为 S2 的"多套预设 + 用户自定义"留好结构；
- 运行时位置：`<exe同级>\data\theme\color.txt`；源码内 `color.txt` 为规范文件与默认值来源，构建时嵌入；
- **健壮性**：解析失败或缺项一律回退内置默认值，绝不影响启动。

> 详见 `计划书_S1_基础版.md` §5.10。

## 六、结论

1. **架构方向不需要改**，四大地基的划分与关键技术路线（湿/干笔迹分离、局部坐标 + 变换矩阵、命令模式、确定性抖动）都成立；

4. 建议在 M0 的 PoC-A 中**顺带采集湿/干笔迹外观差异**，用数据支撑 Q1 决策。
