# 计划书 · S3 插件生态

> 上游基线：`白板开发总路线.md`（v1.0）· 前置：S2 出口准则全部满足
> 期目标：**向第三方开放插件，并让"任何插件在未装任何运行时的机器上都跑得起来"成为可机器验证的事实**
> 工期：**12 周 · 2 人**（≈24 人周 / 5.5 人月）

---

## 一、期目标

1. **开放第三方插件生态**：任意开发者用 JavaScript 写插件，拖入即用；
2. **三条通道成型**：T1 脚本沙箱（第三方主力）、T2 进程内程序集（官方/白名单）、T3 进程外（兜底）；
3. **把"插件必然可运行"变成机器判定**：`wbplugin-verify` 9 项预检 + 干净环境验证流水线 + 7 例负向测试；
4. **守住合规**：插件运行期同样**零注册表写入、exe 同级目录外零写入、不依赖 VC++ 运行时**。

**宿主 API 能力面（T1 脚本唯一可见的一切）**

```js
wb.meta                                   // 插件自身信息
wb.canvas.createShape(type, props) → id   // 创建图形对象
wb.canvas.getSelected() → ShapeView[]     // 只读副本
wb.canvas.updateShape(id, props)
wb.commands.register(name, undoFn, redoFn)
wb.ui.addMenuItem(id, label, fn) / addPanel(id, schema)
wb.math.eval(expr) / solve(exprs) / sample(expr, range)   // C# 原语，性能好
wb.data.readText(relPath) / writeText(relPath, text)      // 仅限 exe 同级 data\ 内，宿主校验
wb.log.info/warn/error(msg)
```
**不存在**：`System.IO`、`System.Net`、`Registry`、`Process`、`Assembly.Load`、任意 P/Invoke。

**PE 导入表扫描的白名单规则（直接决定插件能否在未装 VC++ 运行时的机器上跑）**

| 导入的 DLL | 判定 |
|---|---|
| `ucrtbase.dll`、`api-ms-win-crt-*.dll`、`msvcrt.dll` | ✅ 允许（UCRT 是 Windows 系统组件） |
| Windows 系统 DLL 白名单 / 本机 `System32` 中存在的 DLL | ✅ 允许 |
| **其它任何 DLL（含 `msvcp*.dll` / `vcruntime*.dll`）** | ✅ 允许，**前提是随包携带**；未携带则 ❌ 拒绝 |

> ⚠️ **M0 实测修正**：原规则"导入 `msvcp*/vcruntime*` 一律拒绝"**过严**——app-local 部署 VC++ 运行时是微软支持的方式。正确判据是「依赖可解析性」，详见 `白板开发总路线.md` §4.5 第 5 项。

## 五、7 例负向测试（必须全部优雅失败）

| # | 坏插件 | 断言 |
|---|---|---|
| N1 | TFM 不符（`net10` 以外） | 拒绝 + "插件目标框架不受支持" |
| N2 | 缺托管依赖 | 拒绝 + "缺少 `Xxx.dll`，请随插件一同打包" |
| N3 | 缺原生依赖 | 拒绝 + "缺少 `foo.dll`" |
| N4 | **原生库依赖 VC++ 运行时** | 拒绝 + "插件原生库必须静态链接 C++ 运行时（/MT）" |
| N5 | 夹带契约程序集 | 拒绝 + "插件不得携带 `WhiteBoard.Plugin.Abstractions.dll`" |
| N6 | **调用注册表 API** | 拒绝 + "插件不得访问注册表" |
| N7 | 死循环 / 内存爆炸 | 看门狗终止该插件，**宿主与其他插件不受影响**，记录日志 |

**统一断言**：宿主启动正常、给出中文可读原因、**退出码仍为 0**、其他插件功能正常。

## 六、验收标准

| # | 项 | 标准 |
|---|---|---|
| C1 | 第三方 JS 插件 | 拖入 `.wbp` 即用，无需安装/管理员/重启 |
| C2 | 沙箱隔离 | 插件无法访问文件系统（除 exe 同级 `data\`）、网络、注册表、进程 |
| C3 | 配额看门狗 | 死循环插件被终止，宿主无感知（CPU/内存不异常） |
| C4 | 契约一致性 | 插件实现的 `ITool`/`IPlugin` 与宿主类型完全一致（无静默失效） |
| C5 | 原生库解析 | 插件目录内的原生库可被正确加载；目录外的不被探测 |
| C6 | 预检 9 项 | 全部可自动执行，输出 JSON 报告与退出码 |
| C7 | **PE 扫描** | 能准确识别并拒绝依赖 `msvcp140/vcruntime140` 的原生库 |
| C8 | **免环境冒烟** | 干净环境中零拷贝 → `--self-test` 退出码 0 |
| C9 | 真机矩阵 | 5 类目标环境全部通过 |
| C10 | **负向测试 7 例** | 全部优雅拒绝，退出码 0，其他插件正常 |
| C11 | 合规 | 插件全程：注册表 0 条、exe 同级目录外写入 0 条、不依赖 VC++ 运行时 |
| C12 | 热卸载 | 禁用/卸载插件后无残留（ALC 回收、UI 移除、命令注销） |

## 七、出口准则

1. C1~C12 全部通过，证据归档；
2. 第三方开发者**仅凭文档与 SDK**，在不接触宿主源码的前提下完成一个可用插件（真实外部试用 ≥1 例）；
3. 负向测试 7 例全部纳入 CI 回归；
4. 无遗留 P0/P1 缺陷；
5. WASM 通道 PoC 给出明确结论（通过 → 进 S4；不通过 → 记录原因并关闭）。

## 八、风险与对策

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| R1 | 脚本引擎性能不足以支撑图像类插件 | 中 | 热点原语由宿主 C# 实现，插件只做编排；SDK 文档给出性能指引；S4 视 PoC 补 WASM |
| R2 | 沙箱逃逸（脚本通过宿主 API 间接越权） | 高 | 宿主 API 面严格白名单 + 路径校验 + 单元测试含逃逸用例 + 权限声明比对 |
| R3 | ALC 未真正卸载导致内存泄漏 | 中 | `isCollectible` + 避免静态引用泄漏 + 卸载回归测试 |
| R4 | 预检被绕过（插件用反射动态加载） | 中 | 禁用 API 扫描覆盖 `Assembly.LoadFrom`/`Activator`；T2 仅官方白名单 |
| R5 | 第三方插件质量参差影响口碑 | 中 | SDK 质量清单 + 官方认证标记（S4 做市场准入） |
| R6 | `--self-test` 覆盖面不足 | 中 | 7 例负向测试 + 要求第三方提交时附带自检报告 |
| R7 | WASM 运行时原生库依赖 VC++，破坏 C1 免环境部署 | 中 | PoC 先行；不通过则关闭该通道（不影响 T1/T2 交付） |
