## 二、逐项可行性分析

### PoC-A · 笔迹延迟 —— **可行（高），但"怎么算达标"未定** ⚠️

**技术可行性：高。** WPF 的 `InkCanvas` 走 Windows Ink 湿笔迹通道，直连 MilCore→D3D，这是我们选 WPF 而非 Avalonia 的核心理由。

**但有一个必须正视的架构问题**：湿笔迹只是**一层**。真实应用还需要在其上/下叠加文档对象层、临时辅助层、UI 层。多层合成会侵蚀延迟优势——lindexi 的方案正是"WPF 叠在 Avalonia 上"来救延迟，说明**层数本身就是延迟来源**。

因此 PoC-A 不能只测"裸 InkCanvas"，必须对比三条候选路线：

| 路线 | 做法 | 预期延迟 | 复杂度 | 风险 |
|---|---|---|---|---|
| **A1 · InkCanvas 叠加** | 自绘 `CanvasHost` 在下，`InkCanvas` 透明叠在上 | 最低 | 低 | 两层对齐/闪烁（需等待合成完成再清湿层） |
| **A2 · 单层自绘** | 全部在同一个 `OnRender` 里画，含实时笔迹 | 中 | 中 | 需自己实现压感变宽 + 平滑，可能达不到 1 帧 |
| **A3 · D3DImage + D2D** | WPF 外壳 + D3D 承载 D2D 画布 | 最低 | **高** | 互操作复杂度大，跨 DPI、多屏适配麻烦 |

**建议**：PoC-A 扩为"三路线对比"，多花 2.5 人日，**用数据代替拍板**（M0 总工期由 8 天提到 ~11 人日）。

**⚠️ 验收口径（依决策 D1 + D2）**

应用内打点**测不到**显示链路与面板输出，绝对阈值单独立不住。因此采用**双指标**：

| 指标 | 定义 | 阈值 | 作用 |
|---|---|---|---|
| **绝对** | `WM_POINTER` 时间戳 → 含该笔迹的帧提交（`CompositionTarget.Rendering` / `InkCanvas` 帧） | ≤16.7 ms | 兜底门槛 |
| **相对（关键）** | 我们的画布 vs **裸 `InkCanvas` 参考程序**（同机同屏、同一笔输入）的延迟差 | **≤2 ms** | ⭐ 证明"分层没有引入额外延迟"——这正是 Avalonia 失败的病根 |

**相对指标是本次验收的真正核心**：它把"框架/分层是否引入额外延迟"从主观感受变成可测数字，且不依赖相机等外部设备。

**可行性风险**：触摸采样率与屏幕刷新率是延迟的函数输入。M0 的延迟数据定位为**技术路线可行性结论**；发布前须在目标机型上做一次端到端复测。

### PoC-B · 布尔差集 —— **可行（高），但结果是"不可逆的语义降级"** ⚠️

**技术可行性：高。** `Geometry.Combine(g1, g2, GeometryCombineMode.Exclude)` 是 WPF 内置，**零第三方依赖**——正好同时满足 C1（不依赖目标机预装组件）。

**但有一个必须提前决策的语义问题**：布尔差集的结果是**自由路径**，不是参数化图形。

- 一个矩形被圆擦过之后，它在数学上已经不是矩形了——只能变成 `PolygonObject`（一串顶点）。
- 那么"撤销"之后，它应该恢复成**矩形**（参数化），还是只是**顶点集**？这直接决定命令层怎么设计。
- 三种可选语义：
  | 方案 | 做法 | 优点 | 缺点 |
  |---|---|---|---|
  | **B1 · 立即烘焙** | 擦完即转 `PolygonObject`，命令里保存"原对象快照" | 简单、渲染快 | 渲染与数据都退化，文件变大 |
  | **B2 · 遮罩保留** | 保留原图形 + 附加擦除路径列表，渲染时做差集 | 撤销无损、文件小 | 每次渲染都要算差集，性能风险 |
  | **B3 · 延迟烘焙** | 保留原图形，累计到阈值（如 3 次擦除或顶点数超限）才烘焙 | 折中 | 逻辑最复杂 |
  这是**功能语义决策**，需要你定（见待决策 D7）。

**其他风险**：退化情况（自交、空结果、多块分离、孔洞）需要实测；差集耗时决定"实时切割 vs 抬手结算"（见 D9）。

### PoC-C · 免环境运行与可搬运性 —— **可行（高）** ✅

**技术可行性：高。** .NET 自包含单文件夹天然满足"零拷贝运行"与"整体搬运"。

**关键论证**：C1/C3 要求"不依赖目标机预装组件、数据不落程序文件夹之外"。只要**零写入**（I2/I3）与**无硬编码路径**两条成立，"换一台机器、换一个位置照样能用"就是**逻辑推论**，不需要任何特定机器或复现环境。

因此 PoC-C 拆为四项可立即执行的验证：

| # | 验证 | 方法 | 通过标准 |
|---|---|---|---|
| C1 | **零写入证明** | ProcMon：过滤 `RegSetValue/RegCreateKey/RegDeleteKey` 与 `WriteFile` | 注册表 0 条；exe 同级目录外 0 条（用户显式保存/导出的目标路径除外） |
| C2 | **整体搬运** | 把整个程序文件夹复制到另一位置（含另一台机器），删掉旧位置，再启动 | 配置、最近文件、自动保存**全部可用**；无硬编码路径报错 |
| C3 | **干净环境运行** | 在干净环境（全新虚拟机 / Windows 沙箱 / 未装任何运行时与开发工具的机器）中运行 | 退出码 0，无缺失 DLL 提示 |
| C4 | **不可写降级** | 把程序文件夹设为只读 | 给出中文可读提示并进入只读模式，**不崩溃、不静默降级到系统位置** |

**C2 的价值**：它直接验证"零绝对路径假设"这一核心设计——程序文件夹可以放在任意位置、任意机器。

### PoC-D · PE 导入表扫描 —— **可行（高），且能零依赖实现**

**技术可行性：高。** .NET 内置 `System.Reflection.PortableExecutable.PEReader` 可直接读取 PE 结构：

- 手工解析 **Import Directory**（数据目录索引 1）得到全部导入 DLL 名；
- 解析 **Delay Import Directory**（索引 13）覆盖延迟加载；
- 约 120 行代码，**零第三方依赖**——正好符合我们的 I1 不变量。

**已知局限（必须在设计上承认）**：

| 局限 | 影响 | 缓解 |
|---|---|---|
| 静态扫描看不到 `LoadLibrary` / `NativeLibrary.Load` 的**运行时动态加载** | 恶意/粗心插件可绕过 | 静态扫描 + 禁用 API 扫描（`DllImport`/`NativeLibrary`/`Assembly.LoadFrom`）+ 签名白名单，三层组合 |
| 系统 DLL 白名单需维护 | 漏列会误报（把正常插件判为不合格） | 白名单随 SDK 发布并版本化（见 D10） |
| 只覆盖 PE（.exe/.dll），不覆盖 .NET 程序集的托管依赖 | 需配合第 3 项（托管引用差集） | 已有设计 |

## 三、M0 总体结论

| PoC | 可行性 | 关键前提 | 若不达标的退路 |
|---|---|---|---|
| A 笔迹延迟 | 🟢 高 | 明确的相对基线口径（已定） | ① A3（D3DImage+D2D） ② 重估基线换 C++/Win32 宿主 ③ 调整产品定位（退路顺序已由 D5 确认） |
| B 布尔差集 | 🟢 高 | 确定擦除后的对象语义（P1-D7） | 降级为"整对象删除"（损失功能，不阻塞） |
| C 免环境运行与可搬运性 | 🟢 高 | 无（零写入 + 无硬编码路径即可成立） | 若 C2 失败 → 说明存在硬编码路径，属实现缺陷而非方案缺陷 |
| D PE 扫描 | 🟢 高 | 明确白名单维护方式（P1-D10） | 静态扫描 + 人工审查（降低自动化程度） |

**结论：M0 可以立即开工。四项均无"技术不可行"问题；P0 决策已全部落地。**
