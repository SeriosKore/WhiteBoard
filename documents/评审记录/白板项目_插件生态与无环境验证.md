# 白板项目 · 插件生态方案与"无环境主机"验证设计

> 追加硬要求：**插件生态权重很高** —— 必须能自由加装插件，且**任何插件在无环境主机上都必须能运行、不得报环境缺失**
> 约束不变：Windows 10 · 免环境部署 · 应用及插件均不得写入注册表

---

## 0. 先给结论（含一句必须说清的话）

**可以做到，但前提是把要求从"任何 DLL 都能跑"改写成一个可验收的契约。**

必须直说的一点：

> **在"DLL 插件"模型下，"任意第三方写的任意插件都必然能跑"在工程上无法保证。**
> 因为插件的依赖闭合性由**插件作者**决定，而不是由宿主决定。作者可以引用一个缺失的 NuGet、P/Invoke 一个没带的原生 DLL、或用错目标框架——宿主无论如何都无法凭空变出这些文件。

所以正确的做法是把目标拆成可验收的两条：

| 目标 | 能否 100% 保证 | 实现手段 |
|---|---|---|
| **① 官方/白名单插件**在无环境主机必然可运行 | ✅ **能**（可证明） | 打包规范 + 构建期预检 + 无环境流水线验收 |
| **② 任意第三方插件**在无环境主机必然可运行 | ❌ 不能（DLL 模型下）<br>✅ **能**（沙箱模型下） | 只对第三方开放 **WASM 沙箱通道** |
| **③ 坏插件绝不能搞垮宿主** | ✅ **能** | 加载隔离 + 故障隔离 + 优雅拒绝（附可读原因） |

**核心架构结论：采用"双通道插件体系"——第三方走 WASM 沙箱（结构性保证），官方走进程内 .NET 程序集（配合规范与预检）。** 这样"任何插件都能在无环境主机跑"就从"祈祷"变成"架构上不可能不成立"。

**副作用（重要）**：这个结论同时把宿主的 TFM 选择从 `net48` 推向 **`net10` 自包含**——原因见 §6：只有 .NET 8+ 才能**在程序集解析层拦截注册表 API**，而 .NET Framework 下 `Microsoft.Win32.Registry` 编译在 `mscorlib` 里，拦不住。

## 1. 为什么 DLL 插件模型无法保证"零环境缺失"

插件在无环境主机上失败，实际只有 4 类原因，**全部来自插件自身**：

| 失败类型 | 典型现象 | 宿主能否兜住 |
|---|---|---|
| **① 目标框架不匹配** | 插件编译成 `net10.0`，装进 `net48` 宿主 → `Could not load file or assembly 'System.Runtime, Version=10.0.0.0'` | 可在加载前静态拒绝（读 `TargetFrameworkAttribute`） |
| **② 托管依赖缺失** | 插件用了 `Newtonsoft.Json 13.0.3` 但没随包带 → `FileNotFoundException` | 可在预检阶段列出差集 |
| **③ 原生依赖缺失**（**最高频**） | 插件 P/Invoke `foo.dll` 或引用了 native NuGet，DLL 没带 → `DllNotFoundException`。**即使带了，放在子目录也不会被自动找到**（默认搜索路径不含插件目录） | 宿主可用 `AssemblyDependencyResolver` + `LoadUnmanagedDll` 兜住 |
| **④ 与宿主版本冲突** | 插件带的 `System.Text.Json.dll` 与宿主版本不一致 → `MissingMethodException` / `TypeLoadException` | 用**可回收 ALC + 契约程序集回落**彻底隔离 |

**关键工程事实**：③ 是插件生态的头号杀手，而且它是**宿主可以完全解决**的——只要宿主实现 `LoadUnmanagedDll` 重写，把原生库解析范围锁死在插件目录。这一点旧项目没做到（旧 `PluginManager` 只做了托管程序集复用），必须在新版本补齐。

**旧项目已经踩过的坑，务必继承教训**：
> 旧 README 明确记录："`PluginManager` … 在 `Load` 中复用宿主已加载程序集**以避免 `ITool`/`IPlugin` 类型不一致**"

这正是 ALC 隔离的经典陷阱：插件若加载了自己的 `WhiteBoard.Plugin.Abstractions.dll` 副本，那么插件实现的 `ITool` 与宿主期望的 `ITool` 是**两个不同类型**，`is ITool` 判断恒为 false，插件静默失效。新设计必须把"契约程序集一律回落到默认 ALC"作为**强制规则**（见 §4.4 代码）。

## 2. 唯一能做到 100% 保证的模型：沙箱插件（WASM）

**把插件编译成 `.wasm`，宿主内嵌 WASM 运行时（Wasmtime / WasmEdge / Extism）。**

这样插件的"环境"由宿主提供，且是**结构性**的：

| 保证 | 原因 |
|---|---|
| ✅ 零环境依赖 | wasm 是纯字节码，不含平台原生代码，不可能缺 VC++ / .NET / 系统 DLL |
| ✅ 零 ABI 问题 | 没有 C ABI / 编译器版本 / 构建模式问题 |
| ✅ 零版本冲突 | 插件不携带任何宿主程序集 |
| ✅ **物理上无法写注册表** | WASI 可配置为**无文件系统、无网络、无环境变量**；注册表根本不在能力集里 |
| ✅ 无法搞垮宿主 | 内存沙箱隔离，插件 panic/trap 只终止该实例 |
| ✅ 可静态校验 | 加载前即可读取 imports/exports 声明，能力清单可核对 |
| ✅ 跨语言 | 插件作者可用 Rust / TinyGo / AssemblyScript / C / Zig 编译到 wasm |

**代价（必须承认）**：
- 插件不能直接操作画布每帧渲染，**必须通过宿主提供的 API 间接绘制**；
- 热点算法有 2~10 倍性能损失（但白板插件的热点在宿主，通常是可接受的）；
- 需要多引入一个 WASM 运行时（.NET 侧约 2~4 MB，Qt/Rust 侧 1~3 MB）。

**成熟的现成方案**（不必自研）：
- **Extism**：专门为"宿主 + 多语言 wasm 插件"设计的框架，提供 .NET / C / Rust / Go 等宿主 SDK，插件侧也有多语言 PDK。**推荐首选**。
- **Wasmtime**：功能最全，.NET 绑定（Wasmtime.NET）与 C API 均成熟；Rust 侧是原生主场。
- **WasmEdge / wasm3**：体积更小，适合嵌入。

## 3. 推荐的插件体系：三通道并存

| 通道 | 面向对象 | 载体 | 环境依赖 | 能做什么 | 不能做什么 |
|---|---|---|---|---|---|
| **T1 · WASM 沙箱**<br>（主力，开放给第三方） | 任意开发者 | `.wasm` | **无** | 数学/化学求解器、文件格式导入导出、批量处理、生成图形对象的**数据**、自定义算法、菜单项、设置面板 | 不能直接参与逐帧绘制；不能新增交互式绘图工具（除非宿主提供绘制代理） |
| **T2 · 进程内程序集**<br>（官方/白名单） | 官方与签约伙伴 | `.dll` + 自包含目录 | 宿主提供的运行时 | **全部能力**：新增 `ITool`、新增 `ShapeObject` 子类、面板、命令、菜单 | 一旦写错会拖垮宿主（用隔离 + 预检降低） |
| **T3 · 进程外插件**<br>（兜底/重型/不可信） | 大型第三方 | 独立 `.exe` + 管道 | 由插件方决定 | 重型计算、格式转换、外部集成；崩溃不影响宿主 | 交互延迟高；需定义 IPC 协议 |

### 3.1 能力矩阵（白板场景的实际需求映射）

| 白板需要的扩展点 | T1 WASM | T2 进程内 | T3 进程外 |
|---|:---:|:---:|:---:|
| 新增绘图工具（画笔类交互） | ✗ | ✅ | ✗ |
| 新增图形对象类型 | △（宿主代绘） | ✅ | ✗ |
| 新增菜单项 / 面板 / 设置页 | ✅ | ✅ | △ |
| 注册撤销命令 | ✅ | ✅ | △ |
| 数学/化学求解器 | ✅ | ✅ | ✅ |
| 导入/导出新格式 | ✅ | ✅ | ✅ |
| 图像处理滤镜 | ✅ | ✅ | ✅ |
| 自定义文件解析 | ✅ | ✅ | ✅ |
| 高频逐帧渲染钩子 | ✗ | ✅ | ✗ |

> **产品判断**：白板插件生态的真实需求里，**80% 是"计算与数据"类**（求解器、格式、滤镜、批量），这些 WASM 全包；**只有"新增交互式绘图工具"必须要 T2**。而"新增交互式工具"恰恰是**只有官方/签约伙伴**才有能力做好的事（需要深度理解文档模型与渲染管线）。
> **所以：第三方开放 T1、官方使用 T2，恰好与需求分布吻合。**

### 3.2 插件包格式 `.wbp`（ZIP）

```
DemoPlugin.wbp
├── plugin.json            清单（必需）
├── plugin.wasm            T1 主体
├── icon.svg               (可选)
├── i18n/zh-CN.json        (可选)
├── LICENSE.txt
└── README.md
```

**加装 = 把 `.wbp` 拖进宿主窗口，或解压到 `ext/<id>/`**。宿主自动发现，无需安装程序、无需管理员、无需重启（可回收 ALC / WASM 实例可热卸载）。

### 3.3 `plugin.json` 清单（强制字段）

```json
{
  "id": "com.vendor.demo",
  "name": "示例插件",
  "version": "1.2.0",
  "apiVersion": "1.0",                 // 插件 API 版本，不匹配则拒绝加载
  "hostMinVersion": "1.0.0",
  "runtime": "wasm",                   // wasm | inproc-dotnet | outproc
  "entry": "plugin.wasm",              // T1
  "assembly": "Demo.dll",              // T2
  "entryType": "Demo.Plugin",          // T2
  "targetFramework": "net48",          // T2 必需，必须 ⊆ 宿主提供集合
  "capabilities": ["solver", "import:svg", "panel"],
  "permissions": [],                   // 声明式权限：file.read / file.write / net（默认全空）
  "hostProvided": ["WhiteBoard.Plugin.Abstractions"],
  "nativeDependencies": ["runtimes/win-x64/native/foo.dll"],
  "minHostBuild": 100
}
```

### 3.4 加载流程（发现 → 校验 → 隔离 → 注册 → 可热卸载）

```
启动/拖入 .wbp
   ↓
① 解压到 ext/<id>/（同目录下 .tmp → 原子 rename，避免半装状态）
   ↓
② 读 plugin.json → 校验 apiVersion / hostMinVersion / runtime
   ↓
③ 静态预检（§5 Stage-1，见下）
   ├─ 失败 → 拒绝加载，UI 显示可读原因，写日志，**其他插件不受影响**
   ↓
④ 按 runtime 分派：
   ├─ wasm          → 建 Wasmtime/Extism 实例；WASI 关闭 fs/net/env
   ├─ inproc-dotnet → 建 PluginLoadContext（isCollectible:true）加载
   └─ outproc       → 启动子进程，建立命名管道（**注意：管道不写注册表**）
   ↓
⑤ 调用插件 OnLoad(PluginContext) 注册工具/面板/命令/菜单
   ↓
⑥ 失败隔离：任何异常 → 标记该插件为 failed，卸载其 ALC，宿主继续运行
```

### 3.5 T2 关键实现（把解析范围锁死在插件目录）

```csharp
sealed class PluginLoadContext : AssemblyLoadContext
{
    private readonly AssemblyDependencyResolver _resolver;
    private static readonly HashSet<string> HostProvided = new(StringComparer.OrdinalIgnoreCase)
    {
        // 契约程序集：必须回落默认 ALC，否则 ITool/IPlugin 类型不一致（旧项目的坑）
        "WhiteBoard.Plugin.Abstractions",
        "WhiteBoard.Core",
        // 注册表 API：解析层直接拒绝（仅 .NET 8+ 有效，见 §6）
        "Microsoft.Win32.Registry",
    };

    public PluginLoadContext(string pluginPath) : base(isCollectible: true)
        => _resolver = new AssemblyDependencyResolver(pluginPath);

    protected override Assembly? Load(AssemblyName name)
    {
        if (HostProvided.Contains(name.Name!))
        {
            if (name.Name == "Microsoft.Win32.Registry")
                throw new PluginSecurityException("插件不得访问注册表");
            return null;                     // 回落默认 ALC → 类型一致
        }
        var path = _resolver.ResolveAssemblyToPath(name);   // 只查插件目录
        return path is null ? null : LoadFromAssemblyPath(path);
    }

    // ★ 缺失的原生依赖兜底 —— 插件生态头号杀手
    protected override IntPtr LoadUnmanagedDll(string name)
    {
        var path = _resolver.ResolveUnmanagedDllToPath(name);   // 含 runtimes/<rid>/native/
        return path is null ? IntPtr.Zero : LoadUnmanagedDllFromPath(path);
    }
}
```

**配套铁律**：
1. 插件**不得**携带 `hostProvided` 列表里的任何程序集（自带会造成版本冲突）→ 预检阶段直接拒绝。
2. 插件目录必须**完全自包含**：预检把"插件引用的程序集集合 − 宿主提供集合"与"插件目录实际文件"做差集，**差集非空即拒绝**。
3. 原生依赖必须放在 `runtimes/win-x64/native/`，由 `AssemblyDependencyResolver` 解析；**绝不依赖系统 PATH/DLL 搜索目录**——这正是"无环境主机"上失败的主因。

## 4. 无环境主机的"环境"到底指什么（验收基准必须钉死）

| 缺失项 | 影响谁 | 对策 |
|---|---|---|
| 无 .NET / Java / Python 运行时 | T2 托管插件 | 宿主自包含；契约 TFM 必须 ⊆ 宿主提供 |
| 无 VC++ 2015-2022 可再发行组件 | 原生依赖插件、宿主自身 | 宿主静态链接 CRT；插件原生 DLL 必须静态链接或 app-local 携带 |
| 无 Windows App SDK / WebView2 | 若误用相关框架 | 本方案不使用（已排除） |
| 无开发工具 / SDK | 全部 | 发布包不含任何 PDB/源码/构建脚本 |
| 离线、无管理员权限 | 全部 | 无网络访问、无 UAC 提权 |
| LTSC / 还原卡 / 只读介质 | 全部 | 配置写 exe 同目录，只读时回退 `%LOCALAPPDATA%` |

## 5. 验证流水线（回答"怎么验证任何插件在无环境主机都能跑"）

**5 个阶段，逐级收紧，全部可自动化。**

### Stage 1 · 构建期静态预检（CI 必过，秒级）

宿主随包提供 `wbplugin-verify.exe`，对每个插件目录输出 `verification-report.json`：

| 检查项 | 判定 |
|---|---|
| 1. 读 `TargetFrameworkAttribute` | 必须 ⊆ 宿主提供集合（`net48` 宿主拒收 `net10` 插件） |
| 2. 枚举托管引用 − `hostProvided` | 差集必须为空，或对应的每个文件都在插件目录内实际存在 |
| 3. 扫描 IL 中所有 `DllImport` / P/Invoke | 得到原生依赖清单，逐个校验文件存在且位数为 x64 |
| 4. 扫描禁用 API | `Microsoft.Win32.Registry`、`System.Net.*`、`System.Diagnostics.Process`、`Environment.Exit`、`Assembly.LoadFrom` |
| 5. 检查是否夹带 `hostProvided` 程序集 | 有任何一项即拒绝 |
| 6. `apiVersion` / `hostMinVersion` 兼容性 | 不兼容即拒绝 |
| 7. 签名（可选，推荐） | 官方插件强制签名校验 |

### Stage 2 · 无环境冒烟测试（**Windows Sandbox，最贴近"无环境主机"**）

Win10 Pro 自带 Windows Sandbox：**每次启动都是全新、干净、无开发环境、可断网的一次性容器**——这是验证"无环境部署"最省事的手段。

```xml
<!-- verify.wsb -->
<Configuration>
  <Networking>Disable</Networking>
  <MappedFolders>
    <MappedFolder>
      <HostFolder>C:\build\WhiteBoard-Portable</HostFolder>
      <SandboxFolder>C:\app</SandboxFolder>
      <ReadOnly>true</ReadOnly>
    </MappedFolder>
  </MappedFolders>
  <LogonCommand>
    <Command>cmd /c C:\app\run-verify.cmd</Command>
  </LogonCommand>
</Configuration>
```

宿主内置自检开关，让验证可自动化：

```powershell
# run-verify.cmd  —— 退出码 0 = 通过
C:\app\WhiteBoard.exe --self-test --all-plugins --report C:\app\report.json
# 输出：每个插件的 load / register / selftest 三项结果 + 失败原因
```

### Stage 3 · 真机矩阵（Hyper-V/VMware 快照，周级回归）

| 环境 | 目的 | 期望 |
|---|---|---|
| Win10 22H2 全新安装（有 net48，**无 VC++ redist**，无 SDK，断网） | 主场景 | 宿主 + 全部插件自检通过 |
| Win10 LTSC 2019（仅 .NET 4.7.2） | 老系统 | 只跑**自包含宿主**，自检通过 |
| Win10 22H2 + 卸载 VC++ 2015-2022 | 原生依赖验证 | 若失败 → 暴露未静态链接的组件 |
| 只读介质（U 盘写保护 / 只读共享） | 只读运行 | 配置自动回退 `%LOCALAPPDATA%`，不报错 |
| 3840×1080 超宽触摸屏 | 屏幕适配 | 布局与触控尺寸正确 |

### Stage 4 · 负向测试（**证明"坏插件搞不垮宿主"**）

故意构造 5 个坏插件，断言宿主**必须**：启动正常、给出可读中文原因、退出码 0、其他插件不受影响。

| 坏插件 | 预期行为 |
|---|---|
| TFM 不符（net10 插件装 net48 宿主） | 拒绝加载 + "插件需要 .NET 10，当前宿主提供 .NET Framework 4.8" |
| 缺托管依赖 | 拒绝 + "缺少 Newtonsoft.Json.dll，请将依赖随插件一同打包" |
| 缺原生依赖 | 拒绝 + "缺少 foo.dll" |
| 夹带契约程序集 | 拒绝 + "插件不得携带 WhiteBoard.Plugin.Abstractions.dll" |
| 调用注册表 API | 拒绝 + "插件不得访问注册表" |
| 运行中抛异常 / 死循环 | 宿主捕获并卸载该插件，其余正常；死循环走看门狗超时 |

### Stage 5 · 注册表零写入佐证（宿主 + 插件全程）

- **Process Monitor**：过滤 `Process Name is WhiteBoard.exe` + `RegSetValue/RegCreateKey/RegDeleteKey` → 预期 **0 条**（插件若走 WASM，物理上不可能）。
- **Regshot 差分**：穷尽功能含**加载并运行每个插件** → 预期差异**仅** `MUICache` 下 `<exe路径>.FriendlyAppName / .ApplicationCompany`（Windows 自身行为）。

## 6. ⚠️ 一个改变宿主选型的发现：net48 拦不住注册表 API

"应用及插件都不得写注册表"这条，在两个 TFM 下的**可强制程度完全不同**：

| | `net48` 便携宿主（2~6 MB） | `net10` 自包含宿主（60~85 MB） |
|---|---|---|
| `Microsoft.Win32.Registry` 所在位置 | **`mscorlib.dll` 内** | **独立程序集** |
| 能否在 ALC 解析层拦截 | ❌ **不能**（拦 mscorlib 等于拦掉整个框架） | ✅ **能**（在 `Load` 中抛 `PluginSecurityException`） |
| 插件注册表访问的防线 | 仅静态扫描 + 代码审查 + 人工信任 | **静态扫描 + 运行时解析层拒绝（双保险）** |
| 插件隔离强度 | 中（CAS 已废弃，无法做运行时权限限制） | 高 |
| 交付体积 | 2~6 MB | 60~85 MB |

**结论**：
- 若**插件生态权重高 + "不得写注册表"是硬约束** → **首选 `net10` 自包含宿主**。
- `net48` 便携版仍可保留，但应**降级为"无插件 / 仅官方白名单插件"的轻量发行版**，并在文档中明确"该版本不提供第三方插件沙箱能力"。
- 最佳组合：**主发行版用 net10 自包含（能跑 T1+T2+T3 全通道）**，同时出一个 net48 便携版（仅 T2 官方插件、走静态预检 + 签名白名单）给极致体积场景。

> 注：ALC 拦截是否覆盖框架程序集的所有解析路径，建议在 M0 阶段用一个小 PoC 验证（10 分钟即可确认）。

## 7. 插件权重提高后，三方案重新评分

| 维度（权重） | A · C# + WPF | B · C++ + Qt 6 | C · Rust + D2D |
|---|---:|---:|---:|
| 进程内插件模型 | **⭐⭐⭐⭐⭐** ALC + `AssemblyDependencyResolver` | ⭐⭐ `QPluginLoader` 要求 Qt 大版本/小版本/编译器/构建模式**完全一致**，否则拒绝加载 | ⭐ 无稳定 ABI，需自定 C ABI vtable |
| WASM 宿主能力 | ⭐⭐⭐⭐ Wasmtime.NET / Extism .NET SDK 成熟 | ⭐⭐⭐ wasmtime C API / wasmer 可用 | **⭐⭐⭐⭐⭐ wasmtime 原生（Rust 是 WASM 主场）** |
| 进程外插件 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **"插件必然能跑"可保证性** | **高** | 中（Qt 版本锁定是硬伤） | 高（但仅 WASM 通道） |
| 第三方开发者门槛 | **最低**（C# 开发者最多，SDK 最简单） | 中（须精确匹配 Qt SDK） | 最高 |
| 插件不得写注册表可强制 | **强**（net10 解析层拒绝） | 中（需自写加载器过滤） | 强 |
| **插件生态综合** | **★★★★★** | ★★★ | ★★★☆ |
| **总推荐度（插件高权重）** | **★★★★★（不变，且优势扩大）** | ★★★☆（下降） | ★★★（不变） |

**结论：把插件生态权重提上来后，方案 A（C# + WPF + .NET 10 自包含）的优势不是缩小而是扩大。** 唯一变化是宿主 TFM 从"net48 优先"调整为"**net10 自包含为主 + net48 便携为轻量副版**"。

Qt 的 `QPluginLoader` 有一个天然硬伤：**插件必须用与宿主完全相同的 Qt 版本和编译器构建**，否则加载即失败——这对"开放第三方插件生态"是结构性障碍。Rust 则相反：WASM 通道最完美，但进程内原生插件几乎不可维护。
