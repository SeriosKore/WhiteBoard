# 白板项目 · 零复用重做的三方案架构与打包设计

> 前提修正：**旧项目完全废弃、零复用**，全部功能在新语言/新框架下重新实现。
> 场景不变：Windows 10 终端 · 免环境部署 · **应用不得写入注册表**

---

## 0. 零复用假设下排序怎么变了

上一版把"现有代码复用与团队熟悉度"计入权重，C++ 被压了一头。既然复用率归零，这项作废，**"开发效率 / UI 体系成熟度 / 交付风险"权重上升**，于是：

| | 方案 | 上一版（含复用） | 本版（零复用） |
|---|---|---:|---:|
| 1 | **C# + WPF（.NET）** | 8.6~9.1 | **9.0** |
| 2 | **C++ + Qt 6 Widgets** | 6.7（被复用率拖累） | **8.4** ↑↑ |
| 3 | **Rust + Win32/Direct2D** | 8.1 | **7.9** |
| — | C++ 纯 Win32 + D2D（无 Qt） | 8.9 | 8.2（作为方案 B 的"瘦身变体"） |
| — | C# + Avalonia / WinUI3 / Flutter / Electron | 7.4 / 6.9 / 6.4 / 5.2 | 全部出局（理由不变：合成层延迟或部署模型冲突） |

**结论：仍推荐 C# + WPF 为首选**，但零复用让 **Qt 6 成为非常接近的次选**（如果团队是 C++ 背景、或有跨平台/OEM 诉求，Qt 应直接升为首选）。Rust 只在"体积与延迟优先、UI 可极简"时才值得。

⚠️ 一个必须正视的事实：旧项目 42 个文件、约 7000 行，是在**同一天内（2026/8/30 00:08→08:46）产出的快速原型**，只覆盖"顺利路径"。**生产级实现的代码量大约是它的 2.5~3 倍**（边界处理、IME、多指手势、掌拒、异常恢复、真机适配、性能调优）。下面的复杂度按**生产级**估算。

## 2. 共用逻辑架构（语言无关，7 层）

三个方案的功能拆分完全一致，只是每层的实现技术不同。先给公共架构，后面每个方案给"技术映射 + 源码目录 + 打包产物"。

```
┌──────────────────────────────────────────────────────────┐
│ L1 外壳层 Shell                                           │
│   主窗口 / 顶部工具栏(含溢出菜单) / 右侧目录缩略图 /         │
│   可折叠数学·化学面板 / 对话框 / 悬浮球(不抢焦点) / 设置     │
├──────────────────────────────────────────────────────────┤
│ L2 输入层 Input                                           │
│   统一指针抽象(鼠标/触摸/笔) / 压感 / 双指缩放平移 /         │
│   掌拒 / 触摸面积→橡皮直径(凸包+鞋带公式)                    │
├──────────────────────────────────────────────────────────┤
│ L3 交互层 Tools                                           │
│   ITool 状态机: 画笔 直线 矩形 椭圆 三角 多边形 箭头 文本     │
│   选择(点选/框选/缩放/旋转/克隆/层级) 橡皮(部分擦除)          │
│   几何辅助: 直尺 / 量角器 / 圆规（临时对象，不入文档）         │
├──────────────────────────────────────────────────────────┤
│ L4 命令层 Commands                                        │
│   ICommand / CommandManager（撤销重做 ≥100 步，事务化）      │
├──────────────────────────────────────────────────────────┤
│ L5 文档模型层 Model                                        │
│   Document → Page[] → ShapeObject[]（局部坐标系+旋转矩阵）    │
│   ViewportState / Resources(图片) / ZOrder / 多态序列化      │
├──────────────────────────────────────────────────────────┤
│ L6 渲染层 Render                                          │
│   视口变换 / 可见区裁剪 / 手绘风格(抖动+二次贝塞尔) /         │
│   湿笔迹层 / 渲染缓存 / 高清导出                            │
├──────────────────────────────────────────────────────────┤
│ L7 服务层 Services + 插件宿主                              │
│   Math(表达式解析/Brent 求根/Newton 方程组/函数采样)          │
│   Chemistry(四角标模型+编辑器) / Files(.wb=ZIP) / 导出 PNG   │
│   IPlugin / PluginContext / 插件加载与启停                   │
└──────────────────────────────────────────────────────────┘
```

**三条贯穿全局的设计红线**（无论选哪个方案）：

1. **湿/干笔迹分离**：落笔期间只画在"湿层"（不进入文档、不进撤销栈），抬笔时一次性转成 `FreehandObject` 入文档。这是低延迟的唯一正确做法，也是 Avalonia 方案失败的核心。
2. **模型层不依赖 UI 框架**：`Model/Commands/Geometry/Math/Chemistry/Files` 只依赖基础类型与几何原语，确保可单元测试、可换 UI。
3. **配置只落文件**：exe 同目录 `settings.json`（只读时回退 `%LOCALAPPDATA%`），永不碰注册表。

## 3. 方案 A：C# + WPF（.NET）

### 3.1 目标框架与部署策略

| 版本 | TFM | 用途 | 体积 |
|---|---|---|---|
| **便携版** | `net48` | Win10 1903+（[系统自带 4.8](https://learn.microsoft.com/zh-tw/dotnet/framework/install/on-windows-10)） | **2~6 MB** |
| **兜底版** | `net10.0-windows` 自包含 | LTSC 2019/2016、未更新系统、Win11 混布 | 60~85 MB |

同一套源码多目标框架（`<TargetFrameworks>net48;net10.0-windows</TargetFrameworks>`），共享 `WhiteBoard.Core` 类库。

### 3.2 技术映射

| 层 | WPF 实现要点 |
|---|---|
| L1 外壳 | `Window` + `DockPanel/Grid`；工具栏用 `ToolBar`+溢出；缩略图用 `RenderTargetBitmap`；悬浮球用独立 `Window{ShowActivated=false, Focusable=false}`（与原方案一致，思路正确） |
| L2 输入 | ⚠️ **WPF 无统一 `PointerPressed`**（那是 Microsoft.UI.Xaml 的 API）。需自建 `IPointerSource`，把 `Stylus*`/`Touch*`/`Mouse*` 三路统一为 `PointerEvent{Id, Pos, Pressure, Type}`；双指用 `ManipulationDelta` 或自行按触点计算 |
| L3 工具 | `ITool` 接口 + `ToolManager`，与框架无关的状态机 |
| L4 命令 | 命令模式，与框架无关 |
| L5 模型 | 纯 C#，`System.Text.Json`（net10）/ `Newtonsoft.Json`（net48）多态序列化 |
| L6 渲染 | **`OnRender(DrawingContext)` + 冻结的 `StreamGeometry`**；手绘风格 = 自写抖动 + `QuadraticBezierSegment`；**湿笔迹用 `InkCanvas`**（自带压感 `StylusPoint.PressureFactor`）；导出用 `RenderTargetBitmap` + `PngBitmapEncoder` |
| L6 橡皮擦 | **`Geometry.Combine(a, b, GeometryCombineMode.Exclude)`** —— WPF 原生布尔差集，等价于 SkiaSharp 的 `PathOp.Difference`（[MS Learn](https://learn.microsoft.com/dotnet/desktop/wpf/graphics-multimedia/how-to-create-a-combined-geometry)）；自由画笔切割需自写线段-圆求交 |
| L7 文件 | `.wb` = `System.IO.Compression.ZipArchive`（内置）；图片解码用 **WIC**（PNG/JPG/BMP/GIF/TIFF 内置） |
| L7 插件 | `AssemblyLoadContext`（可回收）+ `plugin.json`，原设计思路可用 |

> ⚠️ **WebP 细节**：Win10 的 WIC **不原生解 WebP**（需商店的 WebP 扩展，离线机房不可靠）。
> 二选一：① 放弃 WebP 支持；② 随包带 `SkiaSharp.dll + libSkiaSharp.dll`（+9 MB）仅用于解码与 PNG 编码。

## 4. 方案 B：C++ + Qt 6 Widgets

零复用前提下 Qt 性价比大幅上升：UI 工具箱（菜单/工具栏/停靠面板/对话框/富文本）开箱即用，`QTabletEvent` 自带压感，`QPainter`/`QOpenGLWidget` 自绘性能足够，`QPluginLoader` 做插件宿主，`QZipReader`/`QZipWriter`（或 miniz）做 `.wb`。

### 4.1 技术映射

| 层 | Qt 实现要点 |
|---|---|
| L1 外壳 | `QMainWindow` + `QToolBar` + `QDockWidget`（右侧面板可折叠）+ `QStackedWidget`（缩略图）；悬浮球用无边框 `QWidget{Qt::Tool | Qt::FramelessWindowHint | Qt::WindowDoesNotAcceptFocus}` |
| L2 输入 | `QTabletEvent`（压感）+ `QTouchEvent`（多指，需 `AA_SynthesizeTouchForUnhandledMouseEvents` 策略调优）+ `QMouseEvent`，统一为自定 `PointerEvent` |
| L3 工具 | `ITool` 抽象类，Qt 无关的状态机 |
| L4 命令 | `QUndoStack` + `QUndoCommand`（**直接用 Qt 的，省 800 行**） |
| L5 模型 | 纯 C++17；`QJsonDocument` 多态序列化 |
| L6 渲染 | `QOpenGLWidget` + `QPainter`（QPainter 有 OpenGL 后端）或纯 `QPainter`；手绘风格自写抖动 + `QPainterPath::quadTo` |
| L6 橡皮擦 | `QPainterPath::subtracted()` —— Qt 原生布尔差集，等价 `PathOp.Difference` |
| L7 文件 | `QZipWriter/QZipReader`（QtGui 私有头，或用 miniz/libzip）；图片 `QImageReader`（**WebP 需 `qwebp.dll` 插件**） |
| L7 插件 | `QPluginLoader` + `Q_DECLARE_INTERFACE`；Qt 插件有稳定接口约定 |

### 4.2 ⚠️ Qt 专属的三个坑（必须提前规避）

1. **`QSettings` 默认写注册表**：`NativeFormat` 在 Windows 上就是 `HKCU\Software\<Org>\<App>`（[Qt 文档](https://doc.qt.io/qt-6/qsettings.html)）。**必须全局改用 `QSettings::IniFormat` + `setPath()` 指向 exe 同目录**，或干脆不用 QSettings 自己写 JSON/INI。这是本约束下 Qt 最大的雷。
2. **`plugins/` 目录名冲突**：Qt 自己的 `platforms/qwindows.dll`、`imageformats/`、`styles/` 必须放 `plugins/` 下，缺 `qwindows.dll` 直接启动失败。业务插件必须换名，例如 `ext/` 或 `addons/`。
3. **LGPL 合规**：动态链接 → 随包发 DLL + 附 LGPL 文本 + 提供可重链接方式，合规成本低；**静态链接单 exe → 必须提供目标文件或购买商业授权**。若产品要卖，务必先定授权路线，否则后期返工。

## 5. 方案 C：Rust + Win32 / Direct2D / DirectWrite

约束满足度最高的方案：`--target x86_64-pc-windows-msvc` + `+crt-static` 得到**单 exe、零外部依赖、无 VC++ 运行时**；`windows-rs` 直达 `WM_POINTER`（压感、掌拒、多指一次拿全）；D2D `ID2D1Geometry::CombineWithGeometry` 提供布尔差集；DirectWrite 处理 CJK。**但它把 UI 成本推到最高。**

### 5.1 技术映射与关键取舍

| 层 | Rust 实现要点 |
|---|---|
| L1 外壳 | ❌ 无成熟桌面 UI 工具箱。两条路：① `egui`（开发快，但中文 IME 与富文本/公式编辑器是短板）；② 自绘轻量控件层 + **原生 Win32 控件**（`EDIT`/`RichEdit`/`Trackbar`）负责所有文本输入 ← **推荐**，因为原生 EDIT 直接解决 IME |
| L2 输入 | `WM_POINTER` 原生处理（比 WPF/Qt 更底层、延迟更低），`PointerInputType` 区分笔/触摸/鼠标，`GetPointerPenInfo` 取压感 |
| L3 工具 | 纯 Rust 状态机 |
| L4 命令 | 自写 `Command` trait + 栈 |
| L5 模型 | `serde` + `serde_json`，`enum` + tag 做多态 |
| L6 渲染 | `windows-rs` 直调 D2D/DWrite；手绘风格自写抖动 + `D2D1_PATH_SEGMENT`；湿笔迹可用 `DirectInk`/`InkPresenter` 或自绘 + 双缓冲 |
| L6 橡皮擦 | `CombineWithGeometry(D2D1_COMBINE_MODE_DIFFERENCE)` |
| L7 文件 | `zip` crate + `image` crate（PNG/JPG/**WebP 支持**）+ `png` crate |
| L7 插件 | ⚠️ Rust 无稳定 ABI，插件必须走 **C ABI + 版本化 vtable**，插件方可以是 C/C++/Rust |

### 5.2 复杂度估算（生产级）

| 模块 | 预估 LOC | 难度 | 说明 |
|---|---:|---:|---|
| L1 外壳（自绘控件层 + 原生控件桥接） | 5,500~6,500 | ★★★★★ | **最大成本项**，从按钮/滑块/下拉/颜色轮全部要造 |
| L2 输入（WM_POINTER 全链路） | 1,000~1,400 | ★★★★ | 底层可控但细节多 |
| L3 工具状态机 | 3,000~3,600 | ★★★ | |
| L4 命令层 | 900~1,200 | ★★ | |
| L5 文档模型 | 1,600~2,000 | ★★★ | serde 多态 |
| L6 渲染（D2D/DWrite 封装 + 湿笔迹） | 2,800~3,400 | ★★★★ | unsafe 边界要收干净 |
| L6b 橡皮擦几何 | 1,000~1,300 | ★★★★★ | |
| L7 数学 | 1,400~1,600 | ★★★ | |
| L7 化学式（含上下标排版） | 1,800~2,200 | ★★★★ | |
| L7 文件（ZIP/图片/PNG/WebP） | 1,000~1,300 | ★★ | |
| L7 插件宿主（C ABI） | 1,300~1,700 | ★★★★ | ABI 稳定性设计 |
| 打包/DPI/兼容 | 600~800 | ★★ | |
| **合计** | **~24,000 行** | | |

**投入**：2 人 × **10 个月**（≈20 人月），且需要**至少 1 人有 Rust 生产经验**，否则风险不可控。
**最难的三件事**：① UI 工具箱从零（占全部工作量的 1/4）；② 中文 IME + 富文本/公式编辑；③ 插件 ABI 与 `unsafe` 边界治理。

## 7. 三方案共用的"部署合规硬清单"

打包时必须逐条核查（这也是"不得改注册表"的落地清单）：

**❌ 禁止**
1. 不写 `HKLM` / `HKCU` 任何键值（除 Windows 自身的 MuiCache 等执行痕迹）。
2. 不做安装器：不写 `Uninstall` 卸载键、不写 `App Paths`、不写自启动 `Run`。
3. 不注册文件关联（`.wb`）与右键菜单 —— 只提供"打开方式"由用户选择（这属用户操作，非应用写入）。
4. 不使用 `QSettings` 的 `NativeFormat` / Java `Preferences` / .NET `Application.UserAppDataRegistry` / ClickOnce / MSIX。
5. 不注册 COM / ActiveX / 加密狗驱动。
6. **不监听端口、不联网、不做遥测与自动更新** —— 否则 Windows 防火墙会写入 `FirewallRules` 并弹窗。
7. 不安装 VC++ 运行时（C++/Rust 静态链接 CRT，或 app-local 携带 DLL）。
8. 不安装 .NET 运行时（自包含，或用系统自带 .NET Framework 4.8）。

**✅ 允许**
1. 配置写 **exe 同目录** `settings.json` / `settings.ini`；目录只读时回退 `%LOCALAPPDATA%\<App>\`。
2. 日志写 exe 同目录或 `%TEMP%`，并可在设置中关闭。
3. 业务插件放 `ext/`（Qt 方案中与 Qt 自身 `plugins/` 严格隔离）。

**🔍 验收证据方法**
- **Regshot 差分**：快照 A → 穷尽功能（画/擦/输入法/导入/存取/导出/插件/退出）→ 快照 B。预期差异**仅** `MUICache` 下的 `<exe路径>.FriendlyAppName / .ApplicationCompany`（系统行为）。
- **Process Monitor**：`Process Name is WhiteBoard.exe` + `Operation is RegSetValue/RegCreateKey/RegDeleteKey` → 预期 **0 条**。
- **离线全新 VM**：未装任何开发工具、断网，复制文件夹双击运行 → 无 UAC、无防火墙弹窗、无缺失 DLL。
- **延迟实测**：高速相机拍"笔尖落纸 → 出墨"，目标 ≤1 帧（16.7 ms）。
