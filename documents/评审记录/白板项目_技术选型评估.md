# 白板项目 技术选型评估

> 场景：Windows 10 终端用户 · **免环境部署**（不装运行时、不装安装包、最好免管理员）
> 附加硬约束：**不允许更改其注册表**
> 参考对象：本工作区已废弃的 C# + Avalonia + SkiaSharp 白板（约 7000 行）

---

## 0. 一句话结论

**语言不该换，该换的是 UI 框架。**

- 现有项目的痛点大概率来自 **Avalonia 的渲染延迟**，而非 C# 本身。林德熙（微软 MVP）实测并公开记录了：Avalonia 在 Windows 上的实时笔迹渲染**比 WPF 落后约 1~2 帧，最差 5 帧**，且他判定这是 **Avalonia 合成渲染的架构性延迟**（Skia → ANGLE → D3D，比 WPF 直连 D3D 多了一层中间商），他的最终方案是"用 WPF 叠一层做湿笔迹"。（[来源](https://blog.lindexi.com/post/Avalonia-%E7%AC%94%E8%BF%B9%E6%B8%B2%E6%9F%93%E5%A4%AA%E6%85%A2%E4%BA%86-%E7%94%A8-WPF-%E5%81%9A%E5%8A%A0%E9%80%9F%E5%B1%82.html)）
- 对白板来说，**笔迹延迟就是产品本身**。选了一个合成层延迟高的框架，等于用错语言背了框架的锅。
- **推荐：C# + WPF，双发布策略**
  - 便携版：`net48`（Win10 1903+ 自带 4.8，[微软官方版本对照表](https://learn.microsoft.com/zh-tw/dotnet/framework/install/on-windows-10)），整包 **2~6 MB**，拷到 U 盘双击即用。
  - 兜底版：`net10.0-windows` 自包含（约 60~80 MB），用于 LTSC / 未打补丁的旧 Win10。
  - 两者都：**不需要安装运行时、不需要管理员、框架自身不写注册表**。
- **技术极限选项**：C++ / Win32 + Direct2D + DirectWrite（静态 CRT），单 exe 3~10 MB、零依赖、笔迹延迟最低 —— 但等于把 7000 行全部重写，交付风险最高。
- **明确不推荐**：WinUI 3 / Windows App SDK（部署模型与"免安装 + 零注册表"直接冲突）、Electron/Tauri/Wails（体积或 WebView2 依赖）、Python（体积 + 杀软误报）、Flutter（非单 exe + Skia 合成层同类延迟风险 + Windows IME 已知缺陷）。

## 1. 前提纠正：失败的是框架，不一定是语言

先把"语言"和"框架/部署模型"三个层次拆开，否则选型一定会再次踩坑：

| 层次 | 本项目现状 | 是否导致废弃 |
|---|---|---|
| **语言** | C# | 几乎无关。C# 的 GC、LINQ、`record`、异步都不影响白板 |
| **UI 框架** | Avalonia 11.3.20 | **高度可疑**：合成层延迟、输入/触摸细节、生态坑 |
| **渲染后端** | SkiaSharp 2.88.9 | 中性。Skia 本身极强，问题在 Avalonia 的 Skia→ANGLE→D3D 合成链路 |
| **部署模型** | 自包含单文件 + `IncludeNativeLibrariesForSelfExtract` | 基本达标：47 MB、双击即用、无注册表 |

判断依据（可复核）：
1. Avalonia 官方设计图上，渲染要经过 Skia 绘制 → Composition → ANGLE → D3D；WPF 是 UI 线程 Geometry → MilCore → D3D 直通。多一层就多一帧。
2. 该文作者的结论是"这不是代码写得好不好的问题，是框架设计带来的延迟性"，且把减少延迟的 PR 未能合入主干。
3. 白板 + 触摸屏 + 4K（希沃类设备）恰恰是最吃"输入→像素"端到端延迟的场景。

**所以：如果这次换语言但继续用 Avalonia/Flutter 这类 Skia 合成型框架，问题会原样复现。**

## 2. 约束条件的严格解读

### 2.1 "无环境部署"的判定清单

真正要同时满足 6 条，缺一条都会在现场翻车：

| # | 要求 | 说明 |
|---|---|---|
| 1 | 不安装任何运行时 | 要么自带运行时（self-contained / 静态链接），要么只用系统预装组件 |
| 2 | 不安装安装包 | 不能依赖 MSI/MSIX/NSIS 的安装流程 |
| 3 | 不需要管理员权限 | 证书、清单 `asInvoker`、不写 Program Files / HKLM |
| 4 | 能放在只读介质运行 | U 盘、只读共享、还原卡环境；配置必须能落回可写位置或内存 |
| 5 | 无网络也能跑 | 机房/内网离线；不能依赖 CDN、字体下载、在线激活 |
| 6 | 首次启动要快 | 不能每次启动都解压几百 MB 到 `%TEMP%` |

第 6 条是很多人忽略的坑：**.NET 单文件自包含若开启 `IncludeNativeLibrariesForSelfExtract`，原生库会在首次启动解压到 `%TEMP%\.net\...`**。微软在 WinUI 3 单文件文档里也明确写了这一点（"dependencies are extracted to a temp directory at first launch — the app is not a zero-extraction binary"），并建议零解压场景改用 **WPF/WinForms**："WPF and WinForms apps support `PublishSingleFile` with a broader set of configurations"。（[Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app?tabs=csharp)）

> 决策：**优先发布为"自包含 + 单文件夹"**（零解压、启动快、U 盘友好）；只有在必须"一个 exe"时才考虑单文件解压模式。

### 2.2 "不允许更改注册表"的边界 —— 这条必须在合同里写清楚

这是本次评估里**最容易变成验收纠纷**的一条。必须指出一个事实：

> **任何带图形界面的 exe 一旦被启动，Windows 自身就会写注册表。**
> 键位：`HKCU\Software\Classes\Local Settings\Software\Microsoft\Windows\Shell\MUICache`
> 内容：`<exe 全路径>.FriendlyAppName` / `.ApplicationCompany`，取自 exe 的版本资源。
> 该键"references execution of programs with a graphical interface, **installed or from a portable executable**"。
> （[artefacts.help · Registry MUICache](https://artefacts.help/windows_registry_muicache.html)）

另外系统还会独立产生：ShimCache / Amcache（HKLM + `Amcache.hve`）、UserAssist/BAM（HKCU）、Prefetch（文件）。这些都是**操作系统自身的行为，不是应用代码所为，应用无法阻止**。

**因此建议把验收口径写成如下三条**（否则需求在物理上不可满足）：

1. 应用不得**创建、修改或删除**任何注册表键值（`HKLM` 与 `HKCU` 均不得），除 Windows 自身执行痕迹外；
2. 应用不得**依赖**注册表存储任何配置、授权或状态（即注册表被还原/清空后，应用功能完全不受影响）；
3. 应用不得要求管理员权限，不得写 `HKLM`。

补充背景（也是这条约束的常见真实动机）：学校机房普遍使用**冰点还原 / 还原卡**，重启即回滚注册表；域策略也可能锁死注册表写入。所以"零注册表"的真实含义通常是 **"配置必须便携、重启不丢、不依赖注册表"**，而不是"绝对不留任何系统痕迹"。

### 2.3 各技术栈的注册表雷区对照表

| 技术栈 | 应用侧是否写注册表 | 具体雷区 | 规避方式 |
|---|---|---|---|
| **C# / .NET 8+ (WPF/WinForms)** | 否 | `Microsoft.Win32.Registry`（你自己不调就没事）；ClickOnce；`Application.UserAppDataRegistry` | 配置写 exe 同目录或 `%LOCALAPPDATA%` |
| **C# / .NET Framework 4.x (WPF)** | 否 | 同上 | 同上 |
| **C++ / Win32 + 静态 CRT** | 否 | 自己调 `RegSetValue` 才写；COM 注册需 `regsvr32` | 不用 COM 注册即可 |
| **Rust (windows-msvc +crt-static)** | 否 | 同上 | — |
| **Qt 6** | **默认会写！** | `QSettings` 的 `NativeFormat` 在 Windows 上就是注册表：`HKCU\Software\<Org>\<App>`（[Qt 官方文档](https://doc.qt.io/qt-6/qsettings.html)） | 必须显式用 `QSettings::IniFormat` |
| **Java / JavaFX** | 可能 | `java.util.prefs.Preferences` 在 Windows 上落到 `HKCU\Software\JavaSoft\Prefs` | 不用 Preferences，改配置文件 |
| **WinUI 3 / Windows App SDK** | **冲突** | MSIX 安装写注册表；"unpackaged" 模式也明确写着"installer-written registry entries... still work" | 与约束直接冲突 |
| **Electron / Tauri / Wails** | 视打包 | NSIS 安装器写 `Uninstall` 卸载键；Tauri/Wails 依赖 **WebView2 运行时**，其安装器写 `HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-...}` 等键 | 便携 zip 可避开；但 WebView2 依赖本身难绕 |
| **Flutter / Python / Go** | 否 | 框架自身不写 | 注意第三方插件 |

**WebView2 特别注意**：Windows 11 才把它作为系统组件内置；Windows 10 上"绝大多数设备有，但仍有少量没有"，官方要求应用**检测并安装**（离线环境需用 Standalone Installer），检测方式就是读上面那串注册表键。（[Microsoft Learn · WebView2 分发](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)）
→ 对"离线机房 + 零注册表"场景，任何 WebView2 系方案（Tauri/Wails/WinUI3 部分能力）都是自找麻烦。

## 4. 关键方案点评

### ✅ C# + WPF（首选）

**为什么它同时满足两个硬约束**
- 免安装：`net48` 在 Windows 10 **1903 及以上为系统自带**（22H2 自带 4.8）；`net10` 走自包含。
- 零注册表：WPF / .NET 框架本身不写注册表，只要不主动调用 `Microsoft.Win32.Registry`。
- 笔迹：WPF 直连 D3D，且自带 **`InkCanvas` 湿笔迹 + `StylusPoint.PressureFactor` 压感**（[MS Learn](https://learn.microsoft.com/dotnet/api/system.windows.input.styluspoint.pressurefactor)），这正是解决 Avalonia 延迟痛点的官方能力。
- 布尔差集（橡皮擦）：WPF 原生 `Geometry.Combine(..., GeometryCombineMode.Exclude)`（[MS Learn · Combined Geometry](https://learn.microsoft.com/dotnet/desktop/wpf/graphics-multimedia/how-to-create-a-combined-geometry)），无需 SkiaSharp。
- PNG 导出：`PngBitmapEncoder` + `RenderTargetBitmap`，内置。
- 富 UI / 中文 IME：WPF 是 Windows 上最成熟的桌面 UI 栈，原生 IME、`RichTextBox` 开箱可用。
- 插件：`AssemblyLoadContext` 体系原样保留（插件 DLL 加载与注册表无关）。

**代价（必须诚实告知）**
1. **WPF 没有 UWP/Avalonia 式的统一 `PointerPressed/Moved/Released` 事件**（该 API 属于 Microsoft.UI.Xaml / WinUI）。需要自行把 `Stylus*`、`Touch*`、`Mouse*` 三套输入统一成一个 `InputEvent` 抽象层——预计 300~500 行，且正好可以顺手把触摸凸包、双指手势做进去。
2. .NET Framework 4.8 在 **LTSC 2019（1809，仅 4.7.2）/ LTSB 2016（1607，仅 4.6.2）** 上不存在 → 见下面的双发布策略。
3. 4K 分辨率下 WPF 画大量矢量可能有压力；必要时升级为 **WPF 界面 + D3DImage 承载 Direct2D 画布**（托管绑定可用 Vortice.Windows）。
4. 单文件发布若要"零解压"，需放弃 `IncludeNativeLibrariesForSelfExtract`（或直接发布单文件夹）。

**双发布策略（推荐直接照做）**

| 版本 | 目标框架 | 体积 | 适用 | 前提 |
|---|---|---|---|---|
| 便携版 | `net48`（或降到 `net462` 兼容更老系统） | 2~6 MB | U 盘 / 机房 / 老机器 | 目标机为 Win10 1903+（用 net48） |
| 兜底版 | `net10.0-windows` 自包含单文件夹 | 60~80 MB | LTSC、未更新系统、Win11 混布 | 无 |

两个版本共用同一套源码（多目标框架），只是发布参数不同。

### ⚠️ C++ / Win32 + Direct2D（技术最优，成本最高）

- 优势：单 exe 3~10 MB（静态 CRT `/MT`）、零依赖、可直接用 **Windows Ink / WM_POINTER** 拿到最低延迟与压感、`ID2D1Geometry::CombineWithGeometry` 提供布尔差集、DirectWrite 处理 CJK、WIC 解码图片、启动 < 0.3 s。
- 劣势：**7000 行全部作废**；工具栏/面板/颜色轮/悬浮球/对话框全部手写；C++ 内存安全风险；迭代速度慢。
- 适用判断：只有当团队已有 Windows 原生 C++ 积累，或未来要卖给硬件厂商（希沃/鸿合）做深度定制时才值得。

### ⚠️ C# + WinUI 3 / Windows App SDK（与约束冲突）

官方文档自己写明：unpackaged 模式下"traditional Win32 mechanisms such as **installer-written registry entries**... still work"；单文件必须 `IncludeAllContentForSelfExtract=true`，即**首次启动解压到 temp**；且输出体积显著增大。（[MS Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app?tabs=csharp)）
→ 与"免安装 + 零注册表 + 快速启动"三条同时冲突，出局。

### ⚠️ Flutter / Dart

- 免安装基本可以（单文件夹，随包携带依赖），但**不是单 exe**。
- 但两个风险直接命中本项目：① Flutter 在 Windows 上也是 Skia/Impeller 合成链路，与 Avalonia 属"同类延迟风险"；② Windows 桌面端中文 IME 存在长期未闭合缺陷，例如[输入法组合在视图重新获得焦点后中断 (#190042)](https://github.com/flutter/flutter/issues/190042)、[无 TextField 聚焦时输入法仍弹窗 (#181313)](https://github.com/flutter/flutter/issues/181313)。
- 一个中文白板应用把 IME 压在框架 bug 上，风险不可接受。

### ❌ 不建议：Electron / Tauri / Wails / Python / Java

- **Electron**：150~250 MB、内存占用高、弱机机房不友好、Canvas 笔迹延迟差。
- **Tauri / Wails**：体积小，但**强依赖 WebView2 运行时**，Win10 离线环境需要额外安装器（写注册表），直接撞约束。
- **Python + PyInstaller**：200~300 MB、启动慢、**360/火绒等国产杀软对 PyInstaller 包误报率高**——学校现场第一道关就过不去。
- **Java + JavaFX**：`jpackage --type app-image` 确实免安装、不写注册表（避开 `Preferences` API 即可），但 ~80~120 MB、笔迹能力弱、与现有 C# 代码零复用。

## 5. 迁移路径与工作量

现有 7000 行的耦合度实测（按 `using` 指令统计）：

| 类别 | 占比 | 文件 | 迁移动作 |
|---|---:|---|---|
| **纯 C#，零 UI 依赖** | ~16% | `Commands/*`、`Core/PageManager`、`Core/WhiteboardDocument`、`Math/ExpressionParser`、`Math/EquationSolver`、`Plugins/PluginManager`、`Tools/ToolManager` | **直接复用，一行不改** |
| **仅依赖 SkiaSharp** | ~26% | `Objects/*`（8 个）、`Core/WhiteboardController`、`ShapeFactory`、`SkiaMath`、`Rendering/HandDrawnRenderer`、`Rendering/FontUtil`、`Files/FileManager`、`Files/ExportService`、`Math/FunctionGraphBuilder` | 二选一：① 保留 SkiaSharp 做离线导出/PNG 编码；② 机械替换为 WPF `Geometry`/`StreamGeometry`。**算法逻辑（手绘抖动、贝塞尔平滑、路径切割）可 100% 保留** |
| **绑定 Avalonia** | ~50% | `MainWindow`(884)、`Rendering/CanvasView`(498)、`UI/Panels`(453)、`Tools/*`(工具类约 1400)、`UI/ColorWheelControl`、`UI/FloatingBall`、`UI/Dialogs`、`Core/ScreenAdapter`、`Program` | **必须重写**。但其中真正的业务算法（橡皮擦圆-线求交切割、选择变换矩阵、几何工具数学、路径简化）可整段搬运，主要是替换输入事件与绘制 API |

**结论：约 40~45% 的代码可复用或低成本适配，重写量集中在输入层与 UI 层。** 这比换语言（复用率归零）划算得多。

建议的迁移顺序：
1. 建一个 WPF 空壳 + 统一输入抽象层（Stylus/Touch/Mouse → `InputEvent`），跑通"鼠标/触摸/笔都能画一条线"。
2. 搬 `Objects/*` + `HandDrawnRenderer`（保 SkiaSharp 或换 WPF Geometry），跑通手绘风格渲染。
3. 接入 `InkCanvas` 湿笔迹，对比帧延迟（此时应该已经解决问题）。
4. 搬 `Tools/*`（先 SelectTool / BasicTools，再 EraserTool），复用切割算法。
5. 搬 `Math/*`、`Files/*`、`Commands/*`、`Plugins/*`（这几块几乎零成本）。
6. 重写 `MainWindow` / `Panels` / 工具栏 / 缩略图 / 悬浮球 / 屏幕适配。

## 6. 验收与证据方法（把"零注册表"变成可验证的事实）

不要用嘴承诺，用工具出证据：

**① Regshot 差分（最直观）**
1. 干净系统上 Regshot 拍快照 A（勾选 `HKCU\Software`、`HKLM\Software`）；
2. 运行应用并**穷尽功能**：画图、擦除、写字（切输入法）、导入图片、保存/打开 `.wb`、导出 PNG、加载插件、切换页面、拖悬浮球、退出；
3. 拍快照 B，比对。
4. **预期差异：仅 `MUICache` 下的 `<exe路径>.FriendlyAppName / .ApplicationCompany`**（系统行为）。除此之外应当为空。

**② Process Monitor（最严谨）**
- 过滤器：`Process Name is WhiteBoard.exe` + `Operation is RegSetValue/RegCreateKey/RegDeleteKey/RegSetInfoKey`。
- 预期：**0 条记录**。

**③ 绿色性验证（顺带一起做）**
- 同时 diff 文件系统：`%TEMP%`、`%APPDATA%`、`%LOCALAPPDATA%`、`Program Files`。
- 预期：除应用自身目录（或 `%LOCALAPPDATA%\<App>` 的配置）外无新增。

**④ 无环境部署验证**
- 在一台**未装任何开发工具**的全新 Win10 虚拟机（离线、无网络）上，`Ctrl+C / Ctrl+V` 拷贝文件夹后直接双击运行。
- 校验：无 UAC 弹窗、无防火墙弹窗（应用不得监听端口/联网）、无缺失 DLL 提示、启动 < 2 s。

**⑤ 笔迹延迟验证（防止重蹈 Avalonia 覆辙）**
- 用 240/480 fps 手机或高速相机拍摄"笔尖落纸 → 屏幕出墨"，或采样式测量首帧响应；同机对比 WPF/InkCanvas 基线。
- 目标：湿笔迹视觉延迟 ≤ 1 帧（16.7 ms）级别。

**⑥ 兼容性矩阵**
- Win10 22H2 / 21H2 / LTSC 2019 / LTSC 2021、1920×1080 与 3840×1080 超宽触摸屏、鼠标 / 触摸 / 压感笔三类输入。

## 7. 待确认的问题（会影响最终结论）

1. **"不允许更改注册表"的准确口径？**
   是「应用自身零写入、零依赖」（推荐，可验收），还是「系统痕迹也不能有」（物理上不可满足，任何 GUI exe 都会触发 MuiCache）？需要把例外清单写进合同。
2. **目标机是否需要覆盖 Windows 10 LTSC 2019 / 1607？**
   如果是 → 只能走 `net10` 自包含（体积 60~80 MB），`net48` 便携版不够；如果只覆盖 1903+ → 可用 2~6 MB 便携版。
3. **上次废弃的真实原因？**
   是笔迹延迟/手感、Avalonia 的触摸与输入坑、开发效率、还是部署体积？如果**不是**渲染延迟，那本方案的重心（换 WPF）需要重新校准——请给一句话原因，我可以据此调整推荐。
4. **团队是否有 Windows 原生 C++ / Rust 经验？**
   若有且追求极致体积与延迟，C++/D2D 才值得认真评估；否则直接排除。
5. **是否需要向硬件厂商（希沃/鸿合）做 OEM 集成或上架？**
   涉及签名、矿机白名单、可能要求 MSIX —— 那"零注册表"约束本身就要重谈。
