## 二、PoC-D 结论（关键成果）

**问题**：.NET 自包含应用在"未安装 VC++ 可再发行组件"的机器上能否运行？

**方法**：对自包含发布目录的 **398 个 PE 文件**做完整导入表（含延迟加载导入表）扫描。

**结果**：

| 检查项 | 结果 |
|---|---|
| 导入 `vcruntime140.dll` / `msvcp140.dll`（系统版）的 PE 文件 | **0 个** ✅ |
| 未随包携带且目标机没有的非系统 DLL | **0 个** ✅ |
| 非白名单导入 | 241 处，全部是 `mscoree.dll`(239) / `Secur32.dll` / `SspiCli.dll`，**均在 `System32` 中** ✅ |
| 发布目录内的 VC++ 相关文件 | `vcruntime140_cor3.dll`（121.6 KB，**.NET 自带的私有副本**，app-local，**无任何 PE 导入它**） |

**结论**：✅ **宿主侧成立** —— .NET 10 自包含 WPF 应用**不依赖目标机安装 VC++ 可再发行组件**。C1 的核心假设得到验证。

> 附注：`vcruntime140_cor3.dll` 随包携带这件事本身就说明 .NET 采用了 **app-local 部署**策略——把所需的运行时 DLL 放在应用目录里，这正是"免环境"的实现方式。

## 三、4 项需回写设计的实测事实

### 🔴 事实 1：原定的插件预检规则**过严，会误杀合法插件**（已修正）

| | 内容 |
|---|---|
| 原规则 | 插件 PE 导入 `msvcp*.dll` / `vcruntime*.dll` → **一律拒绝**，理由"必须静态链接 CRT" |
| 问题 | **app-local（本地部署）同样是微软支持的 VC++ 运行时分发方式**——把 `msvcp140.dll`/`vcruntime140.dll` 放进插件自己的目录，目标机无需安装可再发行组件即可运行。原规则会把这类**完全合法且能在无环境机器上跑**的插件判为不合格 |
| 修正后 | 判据改为「**依赖是否可解析**」：系统组件（System32 中存在）∪ 随包携带 → 允许；两者都不满足 → 拒绝 |
| 已回写 | `白板开发总路线.md` §4.5 第 5 项、`计划书_S3_插件生态.md`、`tools/WbPeScan` 实现 |

**另一处附带的实现改进**：白名单不再靠手工穷举（穷举必然漏，例如 `mscoree.dll` 一度造成 241 处误报），改为**「白名单 ∪ 本机 System32 中实际存在」**——这也更贴合工具要回答的问题："在**这样一台**机器上能不能跑"。

### 🟠 事实 2：`CodePagesEncodingProvider` 无需任何 NuGet 包

编码回退方案（UTF-8 失败 → 系统 ANSI/GBK）依赖 `CodePagesEncodingProvider`。实测：**它在 .NET 10 共享框架内，直接可用，零依赖**。

→ 意味着"编码兼容"这条需求**不引入任何第三方包**，与 I1（零第三方原生库）零冲突。✅

### 🟠 事实 3：WinExe 的 stdout 与退出码是 CI 的坑（已解决）

| 现象 | 原因 | 解决 |
|---|---|---|
| `WhiteBoard.exe --self-test` 输出看不到、`$LASTEXITCODE` 为空 | WPF 应用是 **GUI 子系统**，从控制台启动时不分配控制台；且 PowerShell 用 `&` 调用 GUI 程序**不会等待** | ① 应用内 `AttachConsole(ATTACH_PARENT_PROCESS)` 并重开 stdout/stderr；② 脚本侧用 `Start-Process -Wait -PassThru` 取退出码；③ 同时写报告文件 |

> **这条必须记住**：S3 的插件自检、S4 的批量部署验证都会走这条路。已在 `SelfTest.cs` 与 `verify.ps1` 中固化。

### 🟠 事实 4：**我们自己的构建脚本踩了编码坑**——恰好印证了设计规则

用 Windows PowerShell 5.1 执行无 BOM 的 UTF-8 脚本时，中文按 ANSI 解读变成乱码，且**某处字节序列把引号吞掉**，导致语法错误：

```
+ ... cious.Count -eq 0) { '鏈彂鐜? } else { ... }
The string is missing the terminator: ".
```

**这正是 `计划书_S1` §5.10 里我为用户文件定的规则**（"写入 UTF-8 带 BOM，读取先剥 BOM 再 UTF-8 再回退 ANSI"）。

→ 规则本身是对的，**现在把它同样应用到我们自己的 `.ps1` 脚本**：所有含中文的脚本必须以 **UTF-8 with BOM** 保存（已在 `verify.ps1` / `build.ps1` 落实）。

## 六-C、决策：笔迹与图形改平滑风（已解决湿/干突变）

### 决策依据

PoC-A 人工核验确认：湿笔迹（`InkCanvas` 平滑）与干笔迹（自研手绘抖动）在抬笔瞬间的外观差异**非常明显**，会被当成 bug。

**决策（已记入总路线 ADR-09）：笔迹与图形一律采用平滑风，放弃手绘抖动风。**
> ⚠️ 这是对原始需求"所有图形采用手绘风格渲染"的**变更**，已由需求方确认。

### 验证结果（`SelfCheck.cs` 新增，可复现）

同一组 160 点 + 同一份 `DrawingAttributes`（线宽 6、压感变宽开），三条"干"渲染路径与 `InkCanvas` 的"湿"渲染**逐像素比对**：

| 干笔迹渲染方式 | 差异像素 | 占比 | 结论 |
|---|---:|---:|---|
| `stroke.Draw(dc)` | **0** | **0.000%** | ✅ 完全一致 |
| `dc.DrawGeometry(brush, null, stroke.GetGeometry())` | **0** | **0.000%** | ✅ **采用此方案** |
| `dc.DrawGeometry(null, pen, stroke.GetGeometry())`（等宽描边） | 14 119 | 1.681% | ❌ 不可用 |

`GetGeometry()` 构建耗时实测 **≈0 ms**（一次构建、冻结复用）。

**为什么"等宽描边"不行**：`InkCanvas` 画的是**压感变宽的填充轮廓**，而描边只能等宽——差 1.68%（约 1.4 万像素）就是这么来的。

### 落地方式（S1 的 T2.4）

1. 文档中保存**原始点 + `DrawingAttributes`**；
2. 渲染时重建 `Stroke` → `GetGeometry()` → **几何填充**；
3. 几何 `Freeze()` 后缓存；平移缩放只换变换矩阵，不重建几何；
4. **"淡入过渡掩盖"不再需要**——抬笔外观零突变。

### 收益

| 项 | 变化 |
|---|---|
| 风险 R6（湿/干差异被当成 bug） | **关闭** |
| S1 的 T2.4（原 `HandDrawnRenderer`） | **4 d → 2.5 d**，且省掉自研抖动/二次贝塞尔/确定性 seed 等一整套算法 |
| S1 WBS | 82.5 → **81 人日**，缓冲 **19%** |
| 原始需求"手绘风格" | 变更为平滑风（ADR-09 已记录） |
| 附带 | 外观更干净；几何更轻（一条填充路径 vs 抖动贝塞尔） |

## 六-D、人工核验发现的第二个问题：湿态比干态粗糙（已修）

### 现象与根因

用户人工核验反馈："**抬笔外观有突变，抬笔前图案比抬笔后粗糙**"。

> ⚠️ 这也暴露了 §六-C 那次验证的**盲区**：我比的是"InkCanvas 渲染**已完成**笔迹" vs 我们的几何（**都是干态**），
> **从没测过书写过程中的湿态**。人工核验抓到了它。

**根因**：`InkCanvas` 在书写过程中使用**增量廉价渲染**，抬笔（`StrokeCollected`）时才切换到完整拟合几何 → 看起来"抬笔后突然变细腻"。

### 修法：湿态也自绘，与干态同一条路径

```
落笔 → 每帧 rebuild：累积点 → Stroke → GetGeometry() → 几何填充 → InvalidateVisual
抬笔 → 点集不再变化 → 几何不再变化 → 外观零跳变
```

### 可行性实测（每帧重建代价）

| 点数 | 重建耗时/帧 | 占 60fps 帧预算 |
|---:|---:|---:|
| 60 | 0.11 ms | 0.6% |
| 150 | 0.16 ms | 0.9% |
| 300 | 0.23 ms | 1.4% |
| 600 | 0.36 ms | 2.2% |
| 1200 | 0.77 ms | 4.6% |
| 2000 | 0.83 ms | 5.0% |

→ **完全可行，无需节流**。

### 架构含义

**不再使用 `InkCanvas` 自带的湿渲染**。输入采集可以由统一输入层完成（PoC-A 里已实现笔/触摸/鼠标三路 + 压感 + 抑制合成鼠标事件），
湿态渲染、干态渲染、缩放、导出全部走**我们自己的矢量管线** → 行为完全可控。

> 这实际上让 PoC-A 的 **A2（单层自绘）成为推荐路线**；A1（InkCanvas 湿 + 自绘干）保留了"抬笔变细腻"的问题，除非放弃 InkCanvas 的湿渲染。
> **最终由真机延迟测量决定**：若 a2 相对 baseline 的延迟差 ≤2 ms，则采用 a2。

## 六-E、抗锯齿与「无损放大 50 倍」（S2 需求）实测

| 缩放 | 渲染耗时 | 笔迹像素 | **边缘过渡宽度** |
|---|---:|---:|---:|
| 1x | 2.4 ms | 2,568 | 3.95 px |
| 10x | 3.1 ms | 83,322 | 3.41 px |
| **50x** | 2.6 ms | 437,567 | **2.71 px** ✅ 抗锯齿正常 |
| 对照组：场景按 1/50 渲染成 24×14 位图后最近邻放大 50 倍 | — | 26,613 | **190.09 px** ❌ 完全糊掉 |

> 度量口径：把像素颜色投影到「背景色 → 笔迹色」连线上得到覆盖率 **t**；
> `0.02 < t < 0.98` 的像素即抗锯齿边缘像素。**边缘过渡宽度 ≈0 = 硬阶梯/锯齿，1~3 px = 抗锯齿正常**。
> （注：背景不透明时 alpha 恒为 255，**不能**用 alpha 判边缘——这一点浪费了我两次测量迭代。）

**结论与三条设计红线**：

1. **几何按世界坐标构建**，缩放平移只改变换矩阵 → 放大是**重绘**而非位图放大；
2. **禁止把画布缓存成固定分辨率位图**（对照组即是反例）；
3. **抗锯齿保持开启**：`EdgeMode = Unspecified`、`BitmapScalingMode = HighQuality`，关闭 `UseLayoutRounding` / `SnapsToDevicePixels`。

**笔宽必须按世界单位存储**，否则放大 50 倍时线宽不跟着变粗；导出用 `pixelsPerUnit` 提高分辨率。
